# 뉴스-KOSIS 사실검증 스키마 정의서

작성일: 2026-07-20  
기준 코드: `src/retrieval_schema.py`, `src/convert_claim_listform_to_schema.py`, `src/hcx_claim_experiment.py`, `src/source_scope_classifier.py`, `src/build_kosis_catalog.py`, `src/retrieval_harness.py`

## 1. 스키마 설계 목적

본 프로젝트의 스키마는 뉴스 문장을 KOSIS 공식 통계 검증 파이프라인에 연결하기 위한 중간 표현이다. 뉴스 문장은 자연어라서 그대로는 KOSIS API 조회에 사용할 수 없으므로, claim, 수치, 단위, 시점, 출처, 통계표 후보를 구조화해 저장한다.

현재 코드는 스키마를 다음 3개 핵심 객체로 분리한다.

| 객체 | 코드 위치 | 역할 |
| --- | --- | --- |
| `Claim` | `src/retrieval_schema.py` | 뉴스가 무엇을 주장했는지 저장 |
| `KOSISTable` | `src/retrieval_schema.py` | KOSIS에 어떤 통계표가 존재하는지 저장 |
| `ClaimTableMapping` | `src/retrieval_schema.py` | claim과 KOSIS 표 후보 또는 gold 매핑을 연결 |

이 구조를 사용하는 이유는 claim 추출, 통계표 검색, 최종 수치 검증의 관심사가 다르기 때문이다.

```text
뉴스 원문
→ Claim 생성
→ KOSISTable catalog 검색
→ ClaimTableMapping 후보 생성
→ KOSIS API 조회
→ 기사 수치와 공식 수치 비교
```

## 2. 전체 데이터 흐름

현재 코드 기준 데이터 흐름은 다음과 같다.

```text

data/kosis_table_tree.json
```

HCX 모델 실험은 별도 입력 CSV를 받아 claim 여부, claim class, observations, 출처를 구조화하고, 이후 코드가 `source_scope`를 다시 계산한다.

```text
data/evaluation/pilot120.csv 등
→ src/hcx_claim_experiment.py
→ output/hcx_experiments/<experiment_id>/predictions.csv
→ output/hcx_experiments/<experiment_id>/metrics.json
```

## 3. Claim 스키마

`Claim`은 뉴스 기사에서 추출된 원자적 주장 1개를 표현한다.

### 3.1 기본 식별 필드

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `claim_id` | string | claim 고유 ID. 변환기에서는 `article_{article_idx}_row_{source_row_number}` 형식으로 생성 |
| `article_idx` | int | 원천 기사 ID |
| `claim_text` | string | 추출된 claim 문장 |
| `source_row_number` | int/null | 원본 후보 행 번호 |
| `article_title` | string/null | 기사 제목 |
| `published_at` | string/null | 기사 작성일 |
| `evidence_quote` | string/null | claim 추출 근거 문구 |

### 3.2 지표·대상 필드

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `indicator_raw` | string/null | 뉴스에 등장한 지표 표현 원문 |
| `indicator_norm` | string/null | 정규화된 지표명. 현재 변환기에서는 자동 확정하지 않음 |
| `population_raw` | string/null | 원문 기준 모집단 또는 대상 |
| `population_norm` | string/null | 정규화된 모집단. 현재 변환기에서는 자동 확정하지 않음 |

예시:

```text
indicator_raw = 비정규직 근로자 수
population_raw = 전체 임금근로자
```

## 4. Claim 수치·단위 스키마

### 4.1 단일 대표값 필드

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `value_raw` | string/null | 대표 수치 원문 |
| `value_num` | float/null | 계산 가능한 숫자로 변환한 대표값 |
| `unit_raw` | string/null | 대표 단위 원문 |
| `unit_norm` | string/null | 정규화 단위 |
| `comparison_value_raw` | string/null | 비교값 원문 |
| `comparison_value_num` | float/null | 비교값 정규화 수치 |
| `comparison_unit_norm` | string/null | 비교값 정규화 단위 |

현재 `src/convert_claim_listform_to_schema.py`는 값과 단위가 각각 1개일 때만 `value_num`, `unit_norm`을 자동 생성한다. 여러 값이 있는 claim은 임의로 첫 번째 값을 대표값으로 축약하지 않고 원본 목록과 observation에 보존한다.

### 4.2 원본 목록 보존 필드

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `raw_value_list` | list[string] | `claim_listform.csv`의 `value_list`를 세미콜론 기준으로 나눈 값 목록 |
| `raw_unit_list` | list[string] | `claim_listform.csv`의 `unit_list`를 세미콜론 기준으로 나눈 단위 목록 |

예시:

```text
raw_value_list = ["92억", "1조8000억", "46억", "100.4"]
raw_unit_list = ["위안", "원", "위안", "%"]
```

### 4.3 수치 정규화 규칙

현재 변환기는 한국어 수치 표현을 다음 기준으로 변환한다.

| 표현 | 정규화 값 |
| --- | ---: |
| `천` | 1,000 |
| `만` | 10,000 |
| `억` | 100,000,000 |
| `조` | 1,000,000,000,000 |
| `천명` | `명` 단위로 1,000배 |
| `만명` | `명` 단위로 10,000배 |
| `천원` | `원` 단위로 1,000배 |
| `만원` | `원` 단위로 10,000배 |
| `억원` | `원` 단위로 100,000,000배 |
| `조원` | `원` 단위로 1,000,000,000,000배 |

`%`와 `%p`는 의미가 다르므로 자동 변환하지 않는다. `%`는 비율 자체이고, `%p`는 비율의 변화폭이다.

## 5. ClaimObservation 스키마

`ClaimObservation`은 claim 안에 포함된 개별 수치 1개를 표현한다. 한 문장 안에 여러 수치가 나올 수 있으므로, 현재 스키마는 수치를 `observations` 배열에 보존한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `observation_id` | string | observation 고유 ID |
| `claim_id` | string | 소속 claim ID |
| `value_raw` | string/null | 수치 원문 |
| `value_num` | float/null | 정규화 수치 |
| `unit_raw` | string/null | 단위 원문 |
| `unit_norm` | string/null | 정규화 단위 |
| `period_raw` | string/null | 시점 원문 |
| `period_start` | string/null | 정규화 시작 시점 |
| `period_end` | string/null | 정규화 종료 시점 |
| `period_type` | string/null | `day`, `month`, `quarter`, `year`, `unknown` 등 |
| `time_compare_raw` | string/null | 비교 시점 원문 |
| `dimension_json` | object | 지역, 연령, 성별 등 분류축 힌트 |
| `relation_type` | string | 값 사이의 관계 유형 |
| `comparison_group` | string/null | 같은 비교 묶음 ID |
| `sequence` | int | claim 내부 순서 |

현재 코드의 `relation_type`은 보수적으로 다음 값을 사용한다.

| 값 | 의미 |
| --- | --- |
| `time_series` | 여러 시점의 값 나열 |
| `comparison_pair` | 기준값과 비교값 |
| `cross_section` | 집단·지역·성별 등 단면 비교 |
| `part_whole` | 부분-전체 관계 |
| `numerator_denominator` | 분자-분모 관계 |
| `multi_indicator` | 여러 지표가 함께 등장 |
| `ranked_list` | 순위형 목록 |
| `range` | 범위 표현 |
| `untyped` | 관계 미확정 |

## 6. 시점 스키마

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `time_ref_raw` | string/null | 원문 시점 표현 |
| `time_start` | string/null | 정규화 시작 시점 |
| `time_end` | string/null | 정규화 종료 시점 |
| `period_type` | string/null | 시점 단위 |
| `time_compare_raw` | string/null | 원문 비교 시점 |
| `time_compare_start` | string/null | 비교 시작 시점 |
| `time_compare_end` | string/null | 비교 종료 시점 |

상대 시점은 기사 작성일 `published_at`을 기준으로 정규화한다. 예를 들어 기사 작성일이 2025년이면 `지난해`는 2024년으로 변환된다. 현재 구현은 `DATE`, `YEAR_MONTH`, `QUARTER`, `YEAR` 패턴을 우선 인식한다.

예시:

```text
time_ref_raw = 지난해 1분기
published_at = 2026-04-10
time_start = 2025-Q1
time_end = 2025-Q1
period_type = quarter
```

## 8. Claim 분류 및 검증 가능성 필드

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `claim_class` | string/null | claim의 성격 분류 |
| `source_scope` | string/null | 출처 기관의 KOSIS 기준 범위 |
| `verifiability_prefilter` | string/null | KOSIS 검증 시도 여부 |
| `list_alignment_status` | string/null | 다중 값 목록 정렬 상태 |
| `extraction_method` | string/null | 추출 방법 |
| `review_status` | string | 검토 상태. 기본값 `pending` |

### 8.1 `claim_class` 허용값

`src/retrieval_schema.py`의 canonical `Claim` 허용값은 다음 10개다.

| 값 | 설명 | KOSIS 직접 검증 여부 |
| --- | --- | --- |
| `집계통계` | 모집단 단위로 집계된 실적 통계 | 검증 대상 |
| `개별사례` | 특정 개인·단일 거래·단일 업체 사례 | 제외 |
| `전망예측` | 미래 전망치 | 제외 |
| `목표계획` | 정책 목표·계획 수치 | 제외 |
| `법령제도` | 법령·제도 기준값 | 제외 |
| `해석수사` | 수치 근거 없는 정성적 표현 | 제외 |
| `사고대응임시통계` | 재난·사고 중 일회성 임시 집계 | 제외 |
| `여론조사` | 지지율·설문 등 조사 결과 | 제외 |
| `통계조사안내` | 통계 조사 제도 설명 | 제외 |
| `정정보도` | 앞선 보도 오류 정정 공지 | 제외 |

주의: `src/hcx_claim_experiment.py`의 실험용 `CLAIM_CLASSES`에는 `노이즈`가 추가되어 있다. 이는 HCX 평가에서 UI 잔재나 추출 오류를 따로 측정하기 위한 실험용 라벨이다. canonical `Claim` validation에는 아직 `노이즈`가 포함되어 있지 않으므로, 최종 저장 전에 `노이즈` 처리 정책을 맞춰야 한다.

### 8.2 `source_scope` 허용값

| 값 | 설명 |
| --- | --- |
| `KOSIS등재` | KOSIS API로 조회 가능한 기관 |
| `공식기관_비KOSIS` | 공식기관이지만 KOSIS 기관 사전에 없음 |
| `민간기관` | 민간 기업·협회·단체 등 |
| `해외기관` | 해외 정부·국제기구 등 |
| `불명` | 기관명 없음 또는 불명확 |

현재 `source_scope`는 LLM이 최종 판단하지 않는다. `src/source_scope_classifier.py`가 `source_org_raw`를 `data/kosis_org_names.json` 기관 사전과 대조해 결정론적으로 계산한다. 이 방식은 모델이 존재하지 않는 KOSIS 기관이나 enum 밖 값을 생성하는 것을 막기 위한 설계다.

### 8.3 `verifiability_prefilter`

현재 정책상 KOSIS 조회 시도 조건은 다음과 같다.

```text
claim_class = 집계통계
AND source_scope = KOSIS등재
→ verifiability_prefilter = 검증시도
```

그 외 경우는 KOSIS 직접 대조 대상에서 제외한다. 이 필드는 LLM에게 묻기보다 후처리 코드로 계산하는 것이 적합하다.

### 8.4 `list_alignment_status`

| 값 | 의미 |
| --- | --- |
| `ALIGNED` | 값·단위·시점 목록이 정렬 가능 |
| `COUNT_MISMATCH` | 값과 단위 또는 시점 개수가 맞지 않음 |
| `LOW_CONFIDENCE` | 정렬 신뢰도가 낮음 |
| `NOT_LIST_FORM` | 나열형 claim이 아님 |
| `SINGLE_VALUE` | 단일 수치 claim |

## 9. KOSISTable 스키마

`KOSISTable`은 KOSIS catalog에 적재할 통계표 메타데이터를 표현한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `table_key` | string | `org_id:tbl_id` 형식의 고유 키 |
| `org_id` | string | KOSIS 기관 ID |
| `org_name` | string | KOSIS 기관명 |
| `tbl_id` | string | KOSIS 통계표 ID |
| `tbl_name` | string | 통계표명 |
| `stat_id` | string/null | 통계 ID |
| `stat_name` | string/null | 통계명 |
| `category_path` | list[string] | 대분류부터 리프까지의 경로 |
| `periods` | list[`KOSISPeriod`] | 수록 기간 정보 |
| `dimensions` | list[`KOSISDimension`] | 분류축 정보 |
| `items` | list[object] | 항목 정보 |
| `units` | list[string] | 표에서 사용되는 단위 |
| `source_name` | string/null | 원자료 출처 |
| `version_status` | string/null | 현재판·구버전 등 버전 상태 |
| `document_text` | string/null | 검색용 문서 텍스트 |
| `embedding_model` | string/null | 임베딩 모델명 |
| `embedding_version` | string/null | 임베딩 버전 |
| `document_version` | string | 검색 문서 버전. 기본값 `table-doc-v1` |

현재 `src/build_kosis_catalog.py`가 생성하는 `data/kosis_catalog_v1.jsonl`은 catalog baseline으로, 다음 필드를 우선 저장한다.

| 생성 필드 | 설명 |
| --- | --- |
| `table_key` | `org_id:tbl_id` |
| `org_id` | 기관 ID |
| `tbl_id` | 표 ID |
| `tbl_name` | 표명 |
| `stat_id` | 통계 ID |
| `category_paths` | 중복 경로를 모두 보존한 경로 목록 |
| `document_text` | `tbl_name + org_id + stat_id + all category paths` |
| `catalog_version` | `kosis-catalog-v1` |

즉 canonical `KOSISTable`은 향후 메타자료 API로 기간, 분류축, 항목, 단위를 확장하기 위한 목표 구조이고, 현재 catalog v1은 lexical retrieval baseline에 필요한 최소 필드를 우선 구현한 상태다.

## 10. ClaimTableMapping 스키마

`ClaimTableMapping`은 claim과 KOSIS 표 후보 또는 gold 선택 결과를 연결한다.

| 필드 | 타입 | 설명 |

| `mapping_id` | string | mapping 고유 ID |

| `sparse_score` | float/null | lexical/BM25 점수 |
| `reranker_score` | float/null | reranker 점수 |
| `metadata_score` | float/null | 단위·기간·분류축 호환성 점수 |
| `matched_dimensions` | object | 매칭된 분류축 |
| `matched_item_id` | string/null | 매칭된 항목 ID |
| `matched_period` | string/null | 매칭된 기간 |
| `matched_unit` | string/null | 매칭된 단위 |
| `status` | string | 후보 상태 |
| `filter_reason` | string/null | 탈락 또는 보류 이유 |
| `is_gold` | bool | 사람이 확정한 gold mapping 여부 |
| `selected` | bool | 최종 선택 여부 |
| `retrieval_version` | string/null | 검색 파이프라인 버전 |

허용되는 `status` 값은 다음과 같다.

| 값 | 의미 |
| --- | --- |
| `CANDIDATE` | 검색 후보 |
| `SELECTED` | 최종 선택 |
| `REJECTED` | 탈락 |
| `AMBIGUOUS` | 후보 간 판단 보류 |
| `NO_KOSIS_MATCH` | KOSIS 매칭 없음 |

현재 `src/convert_claim_listform_to_schema.py`는 입력 CSV에 `gold_tbl_id`와 `gold_org_id`가 모두 있을 때만 gold mapping을 생성한다. 값이 없으면 mapping 파일은 0행일 수 있으며, 이는 오류가 아니다. 자동으로 표를 추측하지 않는 것이 현재 정책이다.

## 11. HCX 실험용 응답 스키마

`src/hcx_claim_experiment.py`는 모델별 claim extraction 성능을 비교하기 위해 별도의 응답 스키마를 사용한다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `is_claim` | boolean | 후보 문장이 claim인지 여부 |
| `claim_class` | enum | claim 성격 분류. 실험용으로 `노이즈` 포함 |
| `indicator_raw` | string/null | 지표 원문 |
| `population` | string/null | 모집단 원문 |
| `observations` | array | 수치 observation 목록 |
| `source_org_raw` | string/null | 문장에 명시된 출처 기관 |
| `source_role` | enum/null | 출처 역할 |
| `evidence_quote` | string | 입력 문장에서 직접 인용한 근거 |

실험용 observation 필드는 다음과 같다.

| 필드 | 설명 |
| --- | --- |
| `value` | 수치 원문 |
| `unit` | 단위 원문 |
| `period` | 시점 표현 |
| `time_compare` | 비교 시점 |
| `dimension` | 지역·연령·성별 등 분류 조건 |
| `relation_type` | 수치 간 관계 |
| `comparison_group` | 비교 묶음 |
| `sequence` | 수치 순서 |

현재 `responseFormat`과 JSON schema 강제는 지원이 확인된 `HCX-007`에만 전달된다. `HCX-DASH-002`, `HCX-005` 등은 JSON-only system prompt에 의존한다. 따라서 모델 비교 시에는 JSON 준수율과 enum 위반율을 함께 확인해야 한다.

## 12. 검증 규칙

`src/retrieval_schema.py`는 외부 validation 패키지 없이 최소 검증을 제공한다.

### 12.1 Claim 검증

주요 검증 규칙:

- `claim_id`는 필수
- `article_idx`는 int
- `claim_text`는 필수
- `claim_class`가 있으면 canonical 허용값 안에 있어야 함
- `source_scope`가 있으면 허용값 안에 있어야 함
- `list_alignment_status`가 있으면 허용값 안에 있어야 함
- attribution의 `role`은 `SOURCE_ROLES` 안에 있어야 함
- observation의 `claim_id`는 상위 `claim_id`와 같아야 함
- claim 내부 `observation_id`는 중복되면 안 됨
- `value_num`이 있으면 `unit_norm`도 있어야 함
- `time_start`가 `time_end`보다 늦으면 안 됨

### 12.2 KOSISTable 검증

주요 검증 규칙:

- `table_key`, `org_id`, `tbl_id`, `tbl_name`은 필수
- `table_key`는 반드시 `org_id:tbl_id` 형식이어야 함

### 12.3 ClaimTableMapping 검증

주요 검증 규칙:

- `rank`는 1 이상
- `status`는 허용값 안에 있어야 함
- `selected=True`이면 `status=SELECTED`여야 함

## 13. 통계표 검색에서의 필드 활용

KOSIS retrieval 단계에서는 다음 필드가 주로 쓰인다.

| 필드 | 활용 방식 |
| --- | --- |
| `claim_class` | `집계통계`만 검색 대상으로 넘김 |
| `source_scope` | `KOSIS등재`일 때 직접 검증 대상으로 처리 |
| `source_org_raw` / `attributions.org_raw` | KOSIS 기관 ID 후보로 정규화 |
| `indicator_raw` | 표명, 통계명, 분류경로 검색 질의 |
| `population_raw` | 분류축 후보 탐색 |
| `time_start`, `time_end`, `period_type` | 수록 기간과 통계 주기 필터 |
| `unit_norm`, `observations.unit_norm` | 단위 호환성 확인 |

현재 `src/retrieval_harness.py`는 lexical baseline으로, gold에서 `gold_verifiability_prefilter=검증시도`인 claim만 사용하고, `gold_org_id`가 있으면 해당 기관으로 후보 pool을 줄인다. 이후 claim text와 catalog의 `document_text` 토큰 겹침을 기반으로 Top-K 후보를 생성한다.

## 14. 수치 검증에서의 필드 활용

최종 수치 검증 엔진은 아직 완성 단계가 아니지만, 현재 스키마상 다음 필드가 공식 수치 비교에 사용될 예정이다.

| 필드 | 활용 방식 |
| --- | --- |
| `observations.value_num` | 기사 수치의 정규화 값 |
| `observations.unit_norm` | 공식 수치와 단위 비교 또는 환산 |
| `observations.period_start`, `observations.period_end` | KOSIS API 조회 기간 |
| `observations.time_compare_raw` | 비교 기준 시점 정렬 |
| `observations.relation_type` | 증감, 나열, 단면 비교 등 계산 방식 선택 |
| `approximation_qualifier` | `약`, `가량`, `N명 중 M명` 등 허용 오차 적용 |
| `ClaimTableMapping.matched_item_id` | KOSIS 항목 코드 선택 |
| `ClaimTableMapping.matched_dimensions` | KOSIS 분류축 선택 |
| `ClaimTableMapping.matched_period` | 조회 기간 확정 |
| `ClaimTableMapping.matched_unit` | 공식 수치 단위 확인 |

중요한 원칙은 최종 판정과 수치 계산을 LLM에게 맡기지 않는 것이다. LLM은 자연어 claim을 구조화하고, 설명 생성에 사용한다. 실제 비교는 KOSIS API 결과와 정규화된 스키마 값을 바탕으로 코드가 수행한다.

## 15. 발표용 요약

발표에서는 다음처럼 설명하면 된다.

> 현재 스키마는 뉴스 claim, KOSIS 통계표, claim-table mapping을 분리한 3계층 구조다. `Claim`은 기사 문장에서 추출한 지표·수치·단위·시점·출처를 저장하고, `KOSISTable`은 KOSIS catalog의 표 메타데이터를 저장하며, `ClaimTableMapping`은 claim과 표 후보의 연결 상태와 검색 점수를 기록한다. 모델은 claim 여부와 구조화 필드를 추출하는 데 사용하고, `source_scope`는 기관 사전 기반 코드로 판정한다. 최종 수치 비교와 판정은 LLM이 아니라 정규화된 수치·단위·시점과 KOSIS API 조회 결과를 코드로 비교하는 방식으로 설계했다.
