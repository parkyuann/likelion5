# 벡터DB 구성 개선안 — KOSIS 통계표 검색

- 작성일: 2026-08-03
- 대상: `kosis_catalog_v4.jsonl`(265,094표) → Qdrant 색인 → 하이브리드 검색
- 과제: 뉴스 주장 1건 → KOSIS 통계표 1개 매핑
- 전제: **정식 골드셋 미구축.** 따라서 본 문서는 단일 정답을 확정하지 않고, **골드셋 확보 시 비교할 후보안**을 근거와 함께 제시한다.

---

## 0. 요약

1. **추가 크롤링은 사실상 불필요하다.** 필요한 재료는 이미 `kosis_table_meta_v4.jsonl`에 있고, 부족한 건 `org_name`(2분)과 통계설명 서술형(7분)뿐이다.
2. **문제는 적재다.** 색인기가 카탈로그 용량의 **8.8%만 읽고 91.2%를 버린다.** 특히 `doc_item_index`(용량의 62.4%)가 색인되지 않아 `"종로구"` 같은 차원값 토큰이 인덱스에 없다.
3. **`tbl_name_vector`는 제거를 권고한다.** `doc_meta_text`의 부분집합인데 임베딩 비용을 2배로 만들고, `tbl_name` 중복률이 51%라 변별력이 낮다.
4. **BM25는 Qdrant 안으로 들여야 한다.** `qdrant-client 1.18.0`이 sparse + `Modifier.IDF` + 서버측 RRF를 지원한다. 현재는 Python에서 매 실행 재구축한다.
5. **SPLADE는 현 시점 부적합**하다(CPU 전용 + 한국어 모델 부재). BM25로 시작하고 BGE-M3 sparse를 나중 대안으로 둔다.

## 1. 현재 상태 (실측)

### 1.1 색인 구성

```
Qdrant  kosis_tables_v2 (local 모드)
 ├ doc_meta_vector (dense 1024) ← doc_meta_text
 └ tbl_name_vector (dense 1024) ← tbl_name
 payload: table_key, org_id, org_name, tbl_id, tbl_name, doc_meta_text, catalog_version

Python (질의 시 매번 재구축)
 └ DocMetaBM25 역색인 ← doc_meta_text
        ↓
   Python RRF 융합
```

### 1.2 정량 진단

| 지표 | 값 | 함의 |
|---|---|---|
| 카탈로그 행 | 265,094 | — |
| 유니크 `doc_meta_text` | 262,660 | 동일 텍스트 표 **4,528행 (2,094그룹)** |
| 유니크 `tbl_name` | 128,832 | **중복률 51%** |
| 임베딩 고유 텍스트 | 391,492 | = 262,660 + 128,832 (교집합 0) |
| `doc_item_index` 용량 비중 | **62.4%** | **색인 안 됨** |
| 색인기가 읽는 비중 | **8.8%** | 91.2%를 읽고 버림 |
| `org_name` null | **64.5%** (170,902) | payload에 빈 값으로 적재됨 |
| `units` 결손 | **29.1%** (77,143) | KOSIS 원본 부재(`err:30`) — 복구 불가 |
| BM25 빈 결과 (300건 실행) | B2 26건 / **B4 65건(21.7%)** | 문서가 짧아 매칭 실패 |

### 1.3 설계 변경 이력 (nayeon `archive/260722`)

| | v1 | v2 (현행) |
|---|---|---|
| BM25 문서 | **`doc_item_index`** | **`doc_meta_text`** |
| BM25 범위 | 265,094 | 515 |
| Dense 범위 | 1,000 | 515 |

**당초 설계(dense=`doc_meta_text` / sparse=`doc_item_index`)는 v1에 구현돼 있었고, v2에서 의도적으로 변경됐다.** 변경 사유는 문서상 **검색 품질이 아니라 경로 간 범위 통일**이며, Recall 비교 근거는 없다(골드셋 부재). 범위 통일은 카탈로그 필터링만으로도 달성 가능했으므로, **두 변경이 불필요하게 묶여 있었다.**

## 2. 설계 원칙 (실측에서 도출)

### 원칙 1 — dense와 sparse의 문서를 분리한다

임베딩은 짧고 의미가 밀집해야 하고, BM25는 매칭될 토큰이 없으면 못 찾는다. 요구가 반대다.

**근거**: `doc_meta_text` 평균 56.7토큰/최대 206토큰(한도 8,192)으로 짧게 유지되는 반면, `doc_item_index`는 최대 222,034자다. 한 필드로 합치면 임베딩이 흐려지고, 나누지 않으면 BM25가 굶는다. 실제로 v2에서 `doc_item_index`를 빼자 **BM25 빈 결과가 21.7%** 발생했다.

### 원칙 2 — 표를 특정하는 정보는 텍스트가 아니라 payload에 있다

**근거**: `doc_meta_text`가 **완전히 동일한 표가 4,528행**이다. 이들은 유사도로 원리적으로 구분 불가하며, **`latest_period`가 87.7%(1,836/2,094그룹)를 구분**한다.

```
[10표 동일] 다빈도 수술 질환별 순위 20위 | 보건 > 건강보험주요수술통계 > … | 질환및순위별
   350:DT_35004_A01   latest=2006
   350:DT_350004N_A003 latest=2018    ← latest_period만 다름
```

나머지 12.2%(256그룹)는 1986·1999년에 끝난 표들이라 2025년 주장과 매칭될 일이 없다.

### 원칙 3 — 중복 벡터를 만들지 않는다

`tbl_name`은 `doc_meta_text`의 첫 요소다. 두 벡터의 상관이 높은데 임베딩 호출은 2배(391,492회)다.

**근거**: `tbl_name` 중복률 51%. 실제 사례로 `tbl_name="회계별"`인 표가 연도·자치단체유형별로 수십 개 존재하며, 이 표의 `doc_meta_text`는 `"회계별 | 정부·재정 > … > 시 | 회계별"`로 **표명·차원명이 중복되고 실질 정보는 경로뿐**이다.

### 원칙 4 — 조사 단위 정보를 표마다 복제하지 않는다

통계설명(조사목적·용어해설)은 `stat_id` 단위다. 조사 1,256개가 표 265,094개를 거느린다(평균 211, **최대 9,767**).

**근거**: 표마다 복제하면 IDF가 붕괴한다.

```
같은 용어의 IDF (N=265,094)
  6표짜리 조사    → 10.62
  9,767표짜리 조사 →  3.30    (3.2배 약화)
```

용어의 변별력이 내용이 아니라 "조사가 큰가"로 결정된다. 또 전체 표의 **49.4%가 500표 이상 대형 조사 소속**이라 피해 범위가 넓다.

### 원칙 5 — 시점은 스칼라 하나로 뭉개지 않는다

**근거**: `periods` 원본은 KOSIS 값이며 실데이터 교차검증을 통과했다.

```
getMeta(PRD): {'PRD_SE':'월','STRT_PRD_DE':'2011.01','END_PRD_DE':'2026.06'}
실조회 2026.06 → DT=24471834 ✅ / 2026.07 → err:30 ✅ 경계 정확
```

반면 파생 필드 `latest_period = max(ends)`는 **우리 가공물**이고 두 겹의 문제가 있다.

- 문자열 max 오류: 16건(0.006%) — 실제 피해는 작음
- **개념 모호**: 주기가 섞인 표에서 "최신"이 정의되지 않음. 예) `월=2026.05`, `년=2026`인 표에서 어느 쪽이 최신인지 결정 불가

→ **주기별로 보존하고, 필터용 정수는 규칙을 명시해 별도 생성**한다.

### 원칙 6 — CPU 환경을 전제한다

**근거**: `torch 2.13.0+cpu`, `CUDA: False`, 12코어. 캐시된 모델은 `bge-reranker-v2-m3` 하나뿐. `kiwipiepy` 미설치(현재 BM25 경로 실행 불가).

→ 학습형 sparse(SPLADE/BGE-M3 lexical)는 26만 문서 인코딩에 수 시간~십수 시간이 걸려 반복 실험에 부적합. **BM25 우선.**

## 3. Payload 설계

`kosis_table_meta_v4.jsonl`에 이미 있는 재료로 구성한다. **추가 크롤링 불필요**(`org_name` 제외).

### 3.0 하드필터 / 소프트필터 판정 기준

커버리지가 100%가 아닌 필드를 `must` 조건으로 걸면, **값이 없는 표가 조용히 후보에서 사라진다.** 결손이 곧 오답이 된다. 따라서 커버리지에 따라 용도를 나눈다.

| 구분 | 조건 | 사용 방식 |
|---|---|---|
| **하드필터** | 커버리지 ≈ 100% | Qdrant `Filter(must=…)` — 후보에서 제외 |
| **소프트필터** | 커버리지 < 100% | 점수 가산/감산, 또는 `should` — **제외하지 않음** |
| **표시·조회용** | 필터 아님 | 결과 반환·후속 API 호출에 사용 |

### 3.1 전체 필드 일람 (커버리지 실측 — 카탈로그 265,094행)

### 3.2 필드별 상세

#### ■ `org_id` — 기관코드 · 100% · **하드필터**

**의미**: 통계를 KOSIS에 게시하는 기관 코드(380종). 예: `101`=국가데이터처, `611`=경기도 수원시.

**효과**: 주장에 "행정안전부에 따르면" 같은 출처가 명시되면 후보를 대폭 축소한다. 다만 `org_id`는 **호스팅 기관**이라 작성 기관과 다를 수 있어(예: 주민등록인구는 `org_id=101`이지만 작성은 행정안전부), 출처 매칭에 단독 사용하면 오차가 생긴다.

**주의**: 표 분포가 편중돼 있다. `--limit`으로 표본을 뽑으면 `table_key` 정렬 앞부분이 `org_id=101`에 몰린다.

#### ■ `org_name` — 기관명 · **35.5%** · **소프트필터** (보강 후 하드)

**의미**: `org_id`를 사람이 읽는 이름으로 옮긴 값. **표에서 받은 게 아니라 `kosis_org_names.json`(181개) 사전 조인 결과**다.

**커버리지 문제**: 64.5%(170,902표)가 null이며, 누락은 전부 기초자치단체다.
```
6xx 46,268 · 7xx 43,366 · 5xx 9,380 · 8xx 4,487
```
`MT_OTITLE`(기관별 뷰)에 시·군·구가 없어 구조적으로 안 채워진다.

**해결**: `getMeta&type=ORG`가 누락분을 정상 반환한다(실증: `611`→경기도 수원시, `711`→전북특별자치도 전주시). **380회 ≈ 2분**이면 ~100%가 되어 **하드필터로 승격**할 수 있다.

**효과**: "수원시 인구" 같은 지역 주장에서 `doc_meta_text`에 기관명이 없어 매칭 근거가 경로뿐인 문제를 해소한다.

#### ■ `stat_id` — 통계조사ID · 100% · **하드필터**

**의미**: 표를 만든 **조사**의 ID. 조사 1,256개가 표 265,094개를 거느린다(평균 211, 중위 94, 최대 9,767).

**효과**
- **동일 조사 표들을 묶어** 후보 다양성을 확보하거나, 반대로 한 조사로 좁힌다.
- 통계설명(§안 3) 부스팅의 **조인 키**.
- "인구총조사 기준" vs "주민등록 기준"처럼 **조사가 다르면 수치가 다른** 경우를 가른다.

**주의**: 조사명(`STAT_NM`)은 별도로 넣을 필요가 없다. **경로 2번째 노드에 99.8% 이미 존재**한다(1,097건 검증).

#### ■ `top_category` — 대분류 · 100% · **하드필터**

**의미**: `category_paths[0][0]`에서 파생. 30종(`인구`,`물가`,`노동`…).

**효과**: 카디널리티가 30으로 낮아 **필터 인덱스 효율이 가장 좋다.** 주장의 주제를 분류할 수 있으면 26만 → 수천~수만으로 즉시 축소된다. 오분류 시 정답이 제외되는 위험이 있으므로, 분류 신뢰도가 낮으면 복수 대분류를 `should`로 거는 편이 안전하다.

#### ■ `category_paths` — 분류 경로 · 100% · **표시용**

**의미**: `["인구","주민등록인구현황"]` 형태의 진열 위치. 구조는 `대분류 > 조사명 > 세부주제 > … > 통계표`.

**경로 개수**: 표당 1개가 거의 전부다. **2개 이상은 119건(0.04%)** — 트리 리프 265,213행이 유니크 265,094표로 줄어든 차이와 정확히 일치한다.

**효과**: 이미 `doc_meta_text`에 들어가 있으므로 검색용으로 중복이다. **결과 화면에 "이 표가 KOSIS 어디에 있는지" 표시**하는 용도로 payload에 둔다.

#### ■ `period_types` — 수록주기 · 100% · **하드필터**

**의미**: 표가 제공하는 주기 목록. 11종(`년`,`2년`,`3년`,`5년`,`월`,`분기`,`반기`,`10년`,`부정기`,`4년`,`일`).

**분포**: 조합 28종이며 편중이 심하다.
```
['년']   190,069 (71.7%)   ['2년']  29,107 (11.0%)   ['3년']  26,460 (10.0%)
['5년']   12,242 ( 4.6%)   ['월']    1,206 ( 0.5%)   ['분기']  1,012 ( 0.4%)
```

**효과**: **"월간"·"분기" 주장에서 결정적이다.** 월 데이터를 가진 표는 1,206+829건 정도로 26만 중 극소수라, `period_types`에 `월`이 있는 표로 좁히면 후보가 200배 이상 줄어든다.

**주의**: 71.7%가 `['년']`이라 연간 주장에는 축소 효과가 거의 없다.

#### ■ `latest_norm` / `earliest_norm` — 수록 시점 경계 · 100% · **하드필터**

**의미**: 데이터가 존재하는 마지막/처음 시점을 **정수로 정규화**한 값. `202606` = 2026년 6월.

**왜 정수인가**: Qdrant `Range` 쿼리는 문자열로 범위 비교가 불가능하다. 원본은 `2026.06`, `2026 1/4`, `20260706`, `2025`로 **형식이 4/7/8자로 뒤섞여** 있어 정규화가 필수다.

정규화 규칙(**가정이므로 문서화 필요**):
```
년   2025      → 202512      분기 2026 1/4 → 202603
월   2026.06   → 202606      반기 2025 2/2 → 202512
일   20260706  → 202607
```

**효과 — payload 중 가장 큰 기여**
1. **노후 표 제외**: `latest_period`가 2015년 이전인 표가 **25.5%(67,516개)** 다. 2025년 주장 검증에서 이들을 제외하면 후보가 1/4 줄어든다.
2. **동일 벡터 표의 유일한 구분자**: `doc_meta_text`가 완전히 같은 표 4,528행(2,094그룹) 중 **87.7%를 `latest_period`가 구분**한다. 예) 「다빈도 수술」 10개 표는 벡터가 동일하고 `latest`만 2006~2018로 다르다.
3. **주장 시점 정합**: "2024년 기준" 주장에 `latest_norm < 202401`인 표를 제외한다.

**신뢰도**: 원본 `periods`는 KOSIS 값이며 실데이터 교차검증을 통과했다(`2026.06`→데이터 존재, `2026.07`→`err:30`). 파생 `latest_norm`만 우리 가공물이다.

#### ■ `period_range` — 주기별 시점 상세 · 100% · **표시·정밀판정**

**의미**: 주기별 시작~종료를 원본 그대로 보존.
```json
{"월":{"start":"2011.01","end":"2026.06","end_norm":202606},
 "년":{"start":"1992","end":"2025","end_norm":202512}}
```

**왜 필요한가**: `latest_period` 스칼라 하나로 뭉개면 정보가 사라진다. 주기가 섞인 표(2,353건)에서 "최신"이 정의되지 않는다 — 예) `월=2026.05`, `년=2026`인 표에서 어느 쪽이 최신인지 결정 불가. **"2026년 3분기" 주장이면 `분기` 항목만 보면 된다.**

#### ■ `units` — 단위 · **70.9%** · **소프트필터** ⚠️

**의미**: 표가 제공하는 측정 단위. 1,678종.
```
%  92,482 (34.9%)   명 41,440 (15.6%)   개 20,238 (7.6%)
건 10,802 ( 4.1%)   천원 8,619 (3.3%)   백만원 6,875 (2.6%)
```

**커버리지 문제 — 복구 불가**: 29.1%(77,143표)가 비어 있고, 원인은 **KOSIS 원본 부재**다(`unit_error` 77,136건이 전부 `err:30 데이터가 존재하지 않습니다`). 재크롤해도 채워지지 않는다.

**따라서 반드시 소프트필터**여야 한다. `must`로 걸면 단위 없는 29%가 통째로 사라지고, 그중 정답이 있으면 회수 불가능해진다.

**효과**: 주장이 `74.7%`인지 `422만5000명`인지에 따라 `%` 표와 `명` 표를 가른다. 지표어가 비슷한 표(「~수」 vs 「~비율」)를 구분하는 신호다. 다만 34.9%가 `%`, 15.6%가 `명`이라 **단독 축소력은 제한적**이고, 다른 필터와 결합해야 의미가 있다.

#### ■ `dim_obj_names` — 차원축 이름 · 99.99% · **하드필터**

**의미**: 표가 가진 분류축 이름 목록. 22,631종.
```
특성별 19,495 · 통계분류 9,366 · 구분별 6,781 · 성별 4,918 · 행정구역별 4,915
시도별 3,249 · 연령별 2,221 · 산업별 2,274
```

**효과**: 주장에 지역·성별·연령 조건이 있으면 **해당 축을 가진 표로 한정**한다. "여성 고용률"이면 `성별` 축이 있는 표여야 한다. `has_region_dim` 같은 **불리언 파생**을 함께 두면 필터가 단순해진다.

**주의**: 상위 빈도 이름 중 `특성별`·`구분별`·`구분1`·`통계분류`는 **내용이 없는 껍데기**다(상위 6개 중 5개). 필터 값으로 쓸 때는 의미 있는 축(`성별`,`행정구역별`,`연령별`,`산업별`,`시도별`)만 화이트리스트로 쓰는 편이 낫다.

#### ■ `dim_count` / `total_value_count` — 표 복잡도 · 100% · **소프트**

**의미**: 차원 개수(1개 29.5% / 2개 58.7% / 3개 9.9% / 4개+ 1.9%)와 차원값 총수.

**효과**: 단순 주장에 초대형 표(읍면동×1세, 차원값 수만 개)가 매칭되는 것을 억제한다. 반대로 세분화된 주장에는 큰 표를 선호하도록 가중할 수 있다. **랭킹 조정용이지 제외 기준이 아니다.**

#### ■ `meta_status` — 메타 보강 상태 · 100% · **하드필터**

**의미**: `enriched`(265,082) / `missing`(12).

**효과**: 메타가 없는 표는 차원·항목·시점이 전부 비어 있어 후속 조회가 불가능하다. 12건뿐이지만 **제외 조건으로 명시**해 두면 파이프라인 하류에서 예외 처리가 줄어든다.

#### ■ `dim_codes` / `item_codes` — 조회 연결용 · 99.99%

**의미**
```json
"dim_codes":  [{"obj_id":"A","obj_nm":"행정구역(시군구)별","values":[{"id":"11110","nm":"종로구"},…]}]
"item_codes": [{"itm_id":"T1","itm_nm":"세대수","unit_nm":"세대"}]
```

**왜 필수인가 — 실증**: v4 메타의 코드만으로 실제 수치 조회에 성공했다.
```
objL1=00, objL2=0, objL3=000, itmId=T10, prdSe=Y, 2023
→ DT=51145884.5 (2023 전국 주민등록연앙인구)
→ 응답 C1/C2/C3가 dimensions[0/1/2]와 정확히 대응
```
**`dimensions` 배열 순서 = `objL1→L8`** (가이드에 없는 사실, 실측 확인).

**현재 상태**: 카탈로그가 `values`에서 `nm`만 남기고 **`id`를 버려서**, 벡터DB 경로로는 표를 맞혀도 `get_data()`를 호출할 수 없다. **검증 파이프라인이 끊겨 있다.**

⚠️ **전량 저장 금지**: 차원값이 표당 수만 개일 수 있다(`doc_item_index` 최대 222,034자). 상위 N개만 넣거나 `table_key`로 외부 저장소를 참조한다.

⚠️ 한글 주기명 → API 코드(`년`→`Y`) 변환표는 메타에 없으므로 별도 작성이 필요하다.

### 3.3 필터 적용 예시

```python
query_filter = models.Filter(
    must=[   # 하드 — 커버리지 100%
        models.FieldCondition(key="meta_status",  match=models.MatchValue(value="enriched")),
        models.FieldCondition(key="latest_norm",  range=models.Range(gte=202001)),
        models.FieldCondition(key="period_types", match=models.MatchAny(any=["월"])),
    ],
    should=[ # 소프트 — 결손 있는 필드는 가산만
        models.FieldCondition(key="units", match=models.MatchAny(any=["%"])),
    ],
)
```

**payload 인덱스 필수**: `create_payload_index`를 호출하지 않으면 필터가 풀스캔이 된다. `org_id`(380종), `top_category`(30종), `period_types`(28조합), `latest_norm`(정수 range)에 인덱스를 생성한다.

### 3.4 표시·리랭킹용

`category_paths`(경로 표시), `doc_meta_text`(리랭커 입력), `item_names`(항목명 제공), `link_url`(= `orgId`+`tblId`로 조립 가능)

현재 리랭커는 문서로 `tbl_name`만 쓰는데 **중복률이 51%**라 상한이 낮다. payload에 `doc_meta_text`·`item_names`가 있으면 리랭커 입력을 개선할 수 있다.

## 4. 벡터 구성 개선안

### 안 1 — 최소 수정 (권장 출발점)

```
A: doc_meta_vector  (dense 1024) ← doc_meta_text
B: item_sparse      (BM25/IDF)   ← doc_item_index   ⭐신규
payload: §3 전체
```

- `tbl_name_vector` **제거** (원칙 3) → 임베딩 호출 391,492 → **262,660 (33% 감소)**
- 당초 v1 설계로 복귀 + payload 확장
- BM25 빈 결과 21.7% 문제 완화 기대

**적합**: 실전 최소 구성. 가장 적은 변경으로 가장 큰 손실(62.4% 사문화)을 회수.

### 안 2 — 3벡터 (안정성 중시)

```
A: doc_meta_vector  (dense)  ← doc_meta_text
B: item_sparse      (BM25)   ← doc_item_index (4,000자 상한)
C: meta_sparse      (BM25)   ← doc_meta_text
payload: §3 전체
```

현행 v2의 `doc_meta_text` BM25를 **버리지 않고 C로 유지**하면서 B를 추가한다. RRF 경로가 늘어 회수율이 올라가지만 색인 용량이 증가한다.

**근거**: `doc_item_index` 최대 222,034자(p99 4,151자)로 극단값이 있어 상한이 필요하다. 상한 없이는 BM25 길이 정규화가 왜곡되고 posting list를 한 표가 지배한다.

### 안 3 — 조사 축 추가 (통계설명 활용 시)

```
A: doc_meta_vector  (dense)
B: item_sparse      (BM25)
C: meta_sparse      (BM25)
payload: + stat_expl_terms (용어해설·조사항목 키워드)
별도: 조사 BM25 인덱스 (문서 1,256개) → 매칭 조사의 표에 부스팅
```

**근거**: 통계설명을 표마다 복제하면 IDF가 붕괴한다(원칙 4). 조사 단위로 **별도 인덱스**를 두면 문서가 1,256개뿐이라 왜곡이 원천적으로 없다.

⚠️ 조사 1개가 최대 9,767표를 거느리므로 **후보 생성이 아니라 부스팅/필터로만** 사용한다.

**얻는 것**: `path`로는 알 수 없는 정보. 예) `dataUserNote`의 *"통계청의 인구센서스와는 조사 대상 및 방법이 다름"* — 주민등록인구 vs 인구총조사를 가르는 신호.

**주의**: `statsNm`은 불필요하다. **경로에 99.8% 이미 포함**돼 있다(1,097건 검증, 경로 2번째 노드).

### 안 4 — 실험용 최대 버전

```
A : doc_meta_vector      (dense) ← 표명+경로+차원명
A2: doc_meta_rich_vector (dense) ← + org_name + 차원값 요약
B : item_sparse_b2       (BM25)  ← 전체 형태소
B2: item_sparse_b4       (BM25)  ← 핵심 성분
C : meta_sparse          (BM25)
payload: §3 전체
```

**목적**: 골드셋 확보 시 벡터를 켜고 끄며 조합을 비교한다. sparse를 이름만 다르게 여러 개 저장해두면 **재색인 없이 토크나이저 조합을 비교**할 수 있다.

⚠️ 26만 × 5벡터는 색인 비용이 크다. **표본 5,000~10,000건으로 먼저 실험**하고 확정 후 전량 색인한다.

### 4.1 비교

| | 벡터 | 임베딩 호출 | 색인 비용 | 적합 |
|---|---|---|---|---|
| 현행 | dense 2 | 391,492 | 기준 | — |
| **안 1** | dense 1 + sparse 1 | **262,660** | **최저** | **실전 출발점** |
| 안 2 | dense 1 + sparse 2 | 262,660 | 중 | 회수율 중시 |
| 안 3 | 안 2 + 조사 인덱스 | 262,660 | 중 | 서술형 활용 |
| 안 4 | dense 2 + sparse 3 | 530,188 | 최고 | 골드셋 대비 실험 |

**임베딩 캐시(`embed_cache.jsonl`)가 있으면 dense는 API 재호출 0회**이며, sparse 추가는 임베딩이 불필요하므로 재색인 비용이 낮다.

## 5. BM25를 Qdrant 안으로 (공통 사항)

### 5.1 현재 문제

| 문제 | 근거 |
|---|---|
| 진실의 원천이 2개 | 코드에 `if qdrant_points != len(bm25.documents): raise ValueError("scope mismatch")` 가드가 존재 |
| 매 실행 역색인 재구축 | `DocMetaBM25.build(catalog, kiwi)` — 26만 건에선 수 분 + 대용량 메모리 |
| 필터가 따로 놈 | BM25는 posting 선형 검사, Qdrant는 인덱스 필터. 300건 배치에선 BM25 필터 미적용 |
| 서버측 융합 불가 | Python으로 결과를 가져와 RRF |
| **현재 실행 불가** | `kiwipiepy` 미설치 |

### 5.2 지원 확인 (`qdrant-client 1.18.0`)

```
SparseVectorParams ✅   Modifier.IDF ✅   Prefetch ✅
Fusion.RRF ✅           Fusion.DBSF ✅
```

### 5.3 동작 원리 (실증)

BM25도 **sparse 벡터**로 표현된다. 축=단어ID, 값=빈도.

```
문서 "…종로구 중구 용산구…" → {4176592673: 1.0, 2135236702: 2.0, …}
질의 "종로구"              → {4176592673: 1.0}
                              ↓ 겹치는 축만 내적
```

역할 분담:

| 단계 | 담당 |
|---|---|
| 형태소 토큰화 | **우리** (Kiwi) |
| TF(빈도) 집계 | **우리** |
| **IDF 계산** | **Qdrant** (`Modifier.IDF`) |
| 길이 정규화·랭킹 | Qdrant |

프로토타입 실행으로 동작을 확인했다(질의 `종로구` → score 0.693, `부산광역시` → 11.784. 같은 1회 등장인데 점수가 다른 것은 Qdrant가 코퍼스 df로 IDF를 계산했기 때문).

### 5.4 통합 후 질의

```python
client.query_points(
    collection_name="kosis_tables_v5",
    prefetch=[
        models.Prefetch(query=dense_vec,  using="doc_meta_vector", limit=50),
        models.Prefetch(query=sparse_vec, using="item_sparse",     limit=50),
    ],
    query=models.FusionQuery(fusion=models.Fusion.RRF),
    query_filter=models.Filter(must=[
        models.FieldCondition(key="latest_norm", range=models.Range(gte=202001)),
        models.FieldCondition(key="period_types", match=models.MatchAny(any=["월"])),
    ]),
    limit=20,
)
```

**한 번의 호출로 dense+sparse 검색, 융합, 필터가 처리된다.** `Fusion.DBSF`와 비교 실험도 가능하다.

## 6. 별도 이슈 — Qdrant local 모드

현재 색인은 `storage.sqlite`에 `points(id TEXT, point BLOB)` 단일 테이블(pickle)이다. 이는 **임베디드 local 모드**이며, `qdrant_client`의 `LocalCollection`은 **인덱싱을 하지 않는다** → 전량 브루트포스.

- 벡터 원본만 265,094 × 2 × 1024 × 4B = **2.17GB RAM 상주**
- 파일 5.46GB (pickle 오버헤드 약 2.5배)

**26만 규모에서는 Docker 서버 모드 + scalar quantization + `on_disk_payload` + payload 인덱스가 사실상 필수**다. 이는 벡터 구성안과 독립적으로 결정할 사항이다.

## 7. SPLADE 등 학습형 sparse 검토

| 항목 | 판정 |
|---|---|
| SPLADE(naver 계열) | ❌ **영어 전용**, 한국어 공식 모델 없음 |
| BGE-M3 lexical weights | ⚠️ 한국어 지원·`FlagEmbedding` 설치됨. 단 **CPU로 26만 인코딩은 수 시간~십수 시간** |
| BM42 | ⚠️ 짧은 문서에 유리하나 검증 사례 부족 |
| **BM25** | ✅ **권장** |

**BM25를 우선하는 추가 근거**

1. **도메인 어휘가 고유명사 중심**이다(`종로구`, `마른오징어`, `기장군`). 정확 토큰 매칭이 유리하며, 학습형 확장은 오히려 희석 위험이 있다.
2. **어휘 불일치는 이미 HyDE가 담당**한다(`나 홀로 사장님` → HCX가 `자영업자_고용형태별_현황` 생성).
3. **골드셋이 없어 검증 불가**하다. 십수 시간 인코딩 후 개선 여부를 말할 수 없다.

→ BM25로 시작, 골드셋 확보 후 BGE-M3 sparse를 대안으로 비교.

```
        ↓
[5] 골드셋 구축               ← 여기까지는 골드셋 없이 진행 가능
        ↓
[6] 안 1~4 비교 실험          Recall@K / MRR
        ↓
[7] 확정 + Docker 서버 모드 전환
```

**핵심은 [3]이다.** 카탈로그를 "지금 쓸 것"이 아니라 **모든 변형의 상위집합**으로 만들어 두면, 이후 벡터·payload 조합은 필드 선택만으로 재조립되어 **재크롤이 영원히 불필요**해진다.

## 부록 B — `doc_meta_text` 차원명 변형 (실험 후보)

현재 `dimension_names`는 **선정 없이 전부**, API 응답 순서대로 들어간다.

```python
dimension_names = [normalize_text(d.get("obj_nm")) for d in dimensions if ...]  # 필터: 빈 값 아님
```

**문제**: 빈도 상위 차원명이 대부분 무의미하다.

```
특성별 19,495 · 통계분류 9,366 · 구분별 6,781 · 구분 4,134 · 구분1 3,473 · 구분2 2,537
성별 4,918 · 행정구역별 4,915 · 시도별 3,249 · 연령별 2,221   ← 의미 있는 것
```

상위 6개 중 5개가 껍데기이며, 19,495개 표가 `특성별`이라는 동일 토큰을 공유해 변별력이 없고 벡터를 서로 끌어당긴다. (단 표명·경로와의 **순수 중복은 5.6%**로 크지 않다.)

| 변형 | 방식 |
|---|---|
| 현행 | 전부 |
| A | 불용 차원명 제외(`특성별`,`구분*`,`통계분류`…) |
| B | `tbl_name`·경로에 이미 있는 차원명 제외 |
| **C** | **차원값 요약 부착** — `특성별` → `특성별(남자,여자,전체)` |
| D | 차원명 전체 제외 (베이스라인) |

**C가 유망**하다. 차원값은 `dimensions[].values[].nm`에 있어 재크롤이 불필요하고, 토큰 여유도 충분하다(평균 56.7 / 최대 206 vs 한도 8,192).
