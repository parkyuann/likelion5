# KOSIS v5 정기 업데이트 가이드 (2주~1달 주기)

작성일: 2026-08-11
관련: `reports/260810_KOSIS_크롤링_v5_실행순서.md`(최초 구축) · `reports/260811_KOSIS_전체표_크롤링_결과보고서.md`(결과)

KOSIS는 계속 갱신된다(표 추가·수정·삭제). 이 문서는 **매번 전부 다시 긁지 않고 직전 세대를
재활용**해 업데이트하는 방법이다. 최초 구축이 아니라 **N번째 갱신**을 다룬다.

---

## 0. 핵심 원리 — 무엇을 재활용하나

두 가지가 비용을 결정한다.

| 단계 | 재활용 방법 | 효과 |
|---|---|---|
| **트리 크롤** | 재활용 불가 (BFS는 매번 전체) | ~56,000콜 / ~5시간 |
| **메타 보강** | `send_de` 로 안 바뀐 표 승계 | **66시간 → ~6시간** |

메타 보강이 압도적으로 비싸다(표당 2~3콜). 여기서 `send_de`(표 최종갱신일)를 직전 세대
메타의 `fetched_at`(수집시각)과 비교해, **안 바뀐 표는 getMeta 를 생략**한다.

실측(2026-08-11, v4→v5): 승계 **90.6%**(260,529건), 실제 조회 27,144건, 6.3시간.
정기 업데이트에서는 2주치 변경분만 재보강하므로 **더 적다**(수천 건 규모 예상).

---

## 1. 세대 관리 — 파일 이름 규칙

매 업데이트를 날짜로 구분한다. `_v5` 는 세대(파이프라인 버전)를, 날짜는 **판(snapshot)**을 뜻한다.

```
data/크롤링_v5/
  tree_v5/                              ← 매번 덮어씀 (최신 트리)
  kosis_table_tree_master_v5.jsonl           ← 최신 마스터 (심볼릭 최신본)
  kosis_table_meta_v5.jsonl             ← 최신 메타
  archive/
    260811/                             ← 이번 판 보관 (다음 업데이트의 '직전 세대')
      kosis_table_tree_master_v5.jsonl
      kosis_table_meta_v5.jsonl
```

> **왜 보관하나**: 다음 업데이트가 "직전 세대"를 `--reuse-meta` / `--prev-master` 로 가리켜야
> 하기 때문. 보관본이 없으면 승계를 못 해 매번 66시간이 된다.

## 2. 업데이트 절차 (매 회 반복)

날짜를 `YYMMDD` 로 둔다 (예: `260825`).

### [1] 직전 판 보관

```bash
mkdir -p data/크롤링_v5/archive/PREV
cp data/크롤링_v5/kosis_table_tree_master_v5.jsonl data/크롤링_v5/archive/PREV/
cp data/크롤링_v5/kosis_table_meta_v5.jsonl   data/크롤링_v5/archive/PREV/
```
(`PREV` = 직전 업데이트 날짜. 최초 갱신이면 v4 파일을 쓴다 — §4)

### [2] 트리 재크롤 (11개 뷰)

```bash
venv/Scripts/python.exe src/크롤링_v5/kosis_tree_crawler_v5.py --preset official --restart
```
`--restart` 로 새로 긁는다. 실패 0 · audit 0 확인:
```bash
venv/Scripts/python.exe src/크롤링_v5/kosis_tree_crawler_v5.py --status
```

### [3] 기관명 갱신 (신규 기관 대비)

```bash
venv/Scripts/python.exe src/크롤링_v5/kosis_org_names_v5.py --include-v4-tree
```
(멱등 — 이미 받은 기관은 건너뜀. 신규 기관만 추가)

### [4] 병합 — 직전 판과 대조

```bash
venv/Scripts/python.exe src/크롤링_v5/kosis_merge_views_v5.py \
    --prev-master data/크롤링_v5/archive/PREV/kosis_table_tree_master_v5.jsonl
```

이때 자동 처리:
- 이번 크롤에 있는 표 → `status: active`
- 직전엔 있었으나 이번에 사라진 표 → **`status: retired`** (삭제 안 함, 과거 검증 이력 보존)

> **분류 밖 표(대원화환율 등)는 마스터에 넣지 않는다.** KOSIS 공식 입장(2026-08-11 답변)이
> "통계목록에 없는 표는 사용하지 말라"이므로, 순수 크롤링분만 유지한다. 조사 근거는
> `data/크롤링_v5/보류_분류밖_표_v5.jsonl` 에 보관돼 있다(병합 대상 아님).
> `probe_indicator_tables_v5.py` / `add_indicator_tables_v5.py` 는 조사용으로만 남긴다.

### [5] 메타 보강 — 직전 메타 승계

```bash
venv/Scripts/python.exe src/크롤링_v5/kosis_meta_enricher_v5.py \
    --reuse-meta data/크롤링_v5/archive/PREV/kosis_table_meta_v5.jsonl
```

**두 판의 `send_de`(일단위 YYYY-MM-DD)를 정밀 비교**해 안 바뀐 표는 getMeta 생략. **변경분만 조회.**
send_de 가 실측 100% 일단위이므로 매월 1일 크롤 시 경계(당일 갱신)만 남고 그것도 극소수.

> retired 표는 크롤에 안 잡히지만 마스터엔 남는다. 메타 보강은 retired 표의 메타를
> 직전 것으로 승계한다(getMeta 하면 err — 삭제된 표이므로).

### [6] 카탈로그·색인 재빌드

(카탈로그/색인 스크립트 작성 후 이어붙임. `status != retired` 만 색인)

## 3. 매 회 나오는 변경 리포트

병합([4])이 자동 출력한다:

```
유니크 표 N건 (active A / retired R)
기존 대비 신규 X | 사라짐 Y
send_de 뷰 간 불일치 Z건 (드리프트 신호)
```

메타 보강([5])이 출력:
```
승계 P | 신규수집 Q | 실패 0
```

이 수치로 "이번 2주간 KOSIS가 얼마나 바뀌었나"를 매번 기록한다.

## 4. 최초 1회 (v4 → v5) 만 다른 점

첫 업데이트는 직전 세대가 v4다. `PREV` 자리에 v4 파일을 쓴다:

```bash
# [5] 최초만:
venv/Scripts/python.exe src/크롤링_v5/kosis_meta_enricher_v5.py \
    --reuse-meta data/kosis_table_meta_v4.jsonl
```
`--prev-master` 는 v4 마스터가 없으므로 생략(첫 판은 retired 대조 대상 없음).

> **첫 판 한계**: v4 메타엔 send_de 가 없어 `fetched_at`(2026-07-23) 근사 승계를 쓴다.
> 경계(2026-07 갱신분)가 낡은 채 승계될 수 있으나, 다음 판에서 send_de 정밀 비교로
> 자동 교정된다. 둘째 판부터는 v5 메타에 send_de 가 있어 이 문제가 없다.

## 5. 주의점

| 항목 | 내용 |
|---|---|
| **API 키 단위 분당 200콜** | 크롤 중 다른 KOSIS 작업 금지. 담당 1인 고정 |
| **직전 판 보관 필수** | archive 를 지우면 승계 불가 → 다음 회 66시간 |
| **retired 는 삭제 아님** | 과거 팩트체크가 참조한 표일 수 있어 tombstone 으로 남김 |
| **분류 밖 표 제외** | 대원화환율 등은 KOSIS 공식 "사용 말라" 입장에 따라 마스터에서 제외. `보류_분류밖_표_v5.jsonl` 에만 보관 |
| **매월 1일 크롤 권장** | send_de 가 일단위라, 1일 크롤 시 경계(당일 갱신)가 최소화됨 |
| **중단·재개** | 모든 스크립트가 체크포인트 지원. 껐다 켜도 이어짐 |
