## 1. 실패 원인 — 두 종류

### ① JSON 파싱 실패 — 74건 (복구 가능 ✅)

KOSIS `getMeta` 응답 JSON 자체가 **규격을 살짝 어겨서** 우리 파서(`json.loads`)가
중간에서 터진 경우다. 원인은 **두 하위 유형**으로, 둘 다 영문명 필드(`ITM_NM_ENG`/
`OBJ_NM_ENG`)에서 KOSIS가 백슬래시를 규격대로 이스케이프하지 않아 생겼다.

**①-a 무효 이스케이프 (67건)** — 백슬래시 뒤에 규격 외 글자. `101:DT_1K50001`(char 39945):
```
..."ITM_NM_ENG":"Manufacture of mixed c\ondiments"...
                                        ▲ \o = JSON에 없는 무효 이스케이프 → Invalid \escape
```
JSON에서 백슬래시 뒤에는 `" \ / b f n r t u`만 올 수 있다. `\o`는 무효라 그 지점에서 중단.

**①-b 값 끝의 홑 백슬래시 (7건)** — 영문명이 백슬래시로 끝나 닫는 따옴표가 먹힘.
`207:DT_2071EZA`(char 1585):
```
..."ITM_NM_ENG":"Forest Land with Trees\","ITM_ID":"..."
                                        ▲ \" 를 '따옴표 글자'로 읽어 문자열이 안 닫힘 → Expecting ',' delimiter
```
`\"`는 겉보기엔 유효한 이스케이프라 ①-a용 교정 규칙이 일부러 안 건드린다. 그래서 별도
규칙이 필요했다(3장 참조).

- 두 유형 모두 **표 데이터(한글 차원명·항목명·값)는 정상 존재**하며, 깨진 건 우리가 어차피
  버리는 영문명뿐이다. 다만 그 한 글자 때문에 응답 전체를 못 읽어 표가 통째로 실패한다.
- ①-a는 `101`(통계청) `DT_1K50001~4`·시도별 `INH_1K50001~4_*`(구산업별) 계열에 집중,

## 2. 왜 그냥 재실행하면 안 긁혔나

크롤러는 재실행 시 `load_done_keys()`로 "이미 처리한 표"를 건너뛴다. 그런데 이 함수는
`table_key`가 있는 **모든** 레코드를 '완료'로 보므로, **실패 레코드(`status:"error"`)도
완료로 취급**돼 재시도 대상에서 빠졌다. → 에러 라인을 걷어내야 재크롤 대상이 된다(3장).

## 3. 조치 ① — 파서 수정 (`src/kosis_client.py`)

응답 파싱을 관대(lenient) 모드로 바꿔, 표준 파싱 실패 시 **깨진 백슬래시 두 유형을
교정**한 뒤 재시도한다. 값은 무손실 보존되며(영문명은 어차피 버림), 유효 이스케이프
(`\n \t \uXXXX` 등)는 건드리지 않는다.

```python
_INVALID_ESCAPE = re.compile(r'\\(?![\\"/bfnrtu])')   # ①-a  \o 등 무효 이스케이프
_DANGLING_BACKSLASH = re.compile(r'\\"(?=\s*[,}\]])')  # ①-b  값 끝 홑 백슬래시(\")

def _loads_lenient(text: str):
    try:
        return json.loads(text)
    except json.JSONDecodeError:
        patched = _INVALID_ESCAPE.sub(r'\\\\', text)
        patched = _DANGLING_BACKSLASH.sub(r'\\\\"', patched)
        return json.loads(patched)
```

`search_tables` / `list_tables` / `get_data` / `get_meta` 네 엔드포인트의 `res.json()`을
모두 `_loads_lenient(res.text)`로 교체했다(동일 문제가 어디서든 재발하지 않도록).

> **교정은 fallback에서만 실행된다.** 정상 응답은 첫 `json.loads`에서 성공하고 끝나므로
> 동작이 바뀌지 않는다(정상표에서 `res.json() == _loads_lenient()` 확인). 교정 규칙이
> 도는 것은 이미 표준 파싱이 실패한 응답뿐이라, 값 안에 정상적인 `",` 를 포함한 문자열은
> 애초에 fallback을 안 타서 오탐이 없다.

## 부록 A. 배경 설명 — 이스케이프란? `\o`는 왜 문제인가

> 처음 보는 팀원도 이해할 수 있게 1장 ①의 원인을 풀어 쓴다.

### A-1. 이스케이프(escape)란

문자열 안에는 **그냥 글자로 넣을 수 없는 특수 문자**가 있다. 이때 백슬래시(`\`)를 앞에
붙여 "이건 특별한 뜻"이라고 표시하는 것이 **이스케이프**다.

JSON 문자열은 큰따옴표로 감싼다(`"..."`). 그래서 문자열 *안에* 큰따옴표를 넣으면 파서가
거기서 문자열이 끝난 줄 안다:

```
"그는 "안녕"이라고 했다"     ← 두 번째 "에서 끝난 걸로 착각 → 깨짐
"그는 \"안녕\"이라고 했다"   ← \" 로 "이건 끝이 아니라 따옴표 글자"라고 표시 → 정상
```

### A-2. JSON이 허용하는 이스케이프는 고정 목록이다

JSON 규격은 백슬래시 뒤에 올 수 있는 글자를 아래로 **못박아** 놓았다. 이 목록에 없는
조합은 전부 **문법 위반**이다.

| 이스케이프 | 의미 |
|---|---|
| `\"` | 큰따옴표 글자 |
| `\\` | 백슬래시 글자 그 자체 |
| `\/` | 슬래시 |
| `\n` `\r` `\t` `\b` `\f` | 줄바꿈·캐리지리턴·탭·백스페이스·폼피드 |
| `\uXXXX` | 유니코드 문자(뒤에 16진수 4자리, 예: `\uAC00` = 가) |

### A-3. 그래서 `\o`가 왜 문제인가

문제의 응답: `"...mixed c\ondiments"`. 여기서 `\o`는 위 목록에 **없다**. 파서 입장에선

> "백슬래시가 나왔으니 뒤에 특별한 글자가 오겠지 → `o`? 이런 이스케이프는 규격에 없다 →
> **문법 오류(`Invalid \escape`)**"

하고 그 자리에서 **응답 전체 파싱을 중단**한다. 뒤에 멀쩡한 데이터가 아무리 많아도, 이
백슬래시 한 개 때문에 표 하나를 통째로 못 읽는다. 원래 의도는 영어 단어 `condiments`
(조미료)였고, 백슬래시는 **들어가면 안 될 군더더기**였다.

### A-4. 이것은 KOSIS 서버의 버그다

정상 JSON이라면 둘 중 하나였어야 한다.
- 백슬래시가 불필요하면 → `condiments`
- 진짜 백슬래시 글자를 담고 싶었다면 → `c\\ondiments` (백슬래시는 `\\`로 이스케이프)

KOSIS는 홑 백슬래시 `\o`를 그대로 내보내 규격을 어겼다(JSON 직렬화 시 이스케이프 처리
누락으로 추정). 표준을 지키는 파서라면 어디서든 거부하는 응답이다. 우리가 KOSIS를 고칠
수는 없으므로, **받은 뒤 우리 쪽에서 교정**한다(3장의 `_loads_lenient`).

### A-5. 교정을 '버리기'가 아니라 '살리기'로 한 이유

무효 `\o`를 고치는 방법은 두 가지다.

| 방법 | 결과 | 성격 |
|---|---|---|
| 백슬래시 버리기 (`sub('', text)`) | `condiments` | "쓰레기다"라고 **추정**해 삭제 |
| **백슬래시 살리기** (`sub(r'\\\\', text)`, 채택) | `c\ondiments` | 받은 값 **무손실** 보존 |

의미로는 `condiments`가 맞지만, `_loads_lenient`는 **모든 응답에 자동 적용**되는 범용
코드라 "이 백슬래시는 버려도 된다"고 일반화할 수 없다. 어떤 필드에 `C:\output` 같은
의도적 백슬래시가 있으면 '버리기'는 데이터를 훼손한다. 그래서 **무슨 값이 오든 한 글자도
잃지 않는 '살리기'** 를 택했다.

무엇보다 이 백슬래시가 나온 필드는 **영문 항목명(`ITM_NM_ENG`)** 인데 크롤러가 이 필드를
애초에 **저장하지 않고 버린다.** 따라서 `condiments`든 `c\ondiments`든 우리 데이터 파일엔
들어가지 않으며, 우리에게 필요한 건 "그 한 글자 때문에 못 읽던 응답 전체를 읽어내는 것"
뿐이라 두 방법의 최종 결과는 동일하다.

### A-6. 두 번째 유형 — 값 끝의 홑 백슬래시(①-b)

1차 재실행 뒤 7건이 다른 에러(`Expecting ',' delimiter`)로 남았다. 원인은 A-1~A-5의 `\o`와
**다른** 형태였다.

```
"ITM_NM_ENG":"Forest Land with Trees\","ITM_ID":"..."
                                     ▲ 값이 백슬래시로 끝남
```

영문명 값이 백슬래시로 끝나는데 KOSIS가 이를 `\\`로 이스케이프하지 않고 `\` 하나로 뒀다.
그러면 뒤따르는 닫는 따옴표와 합쳐져 `\"`가 되고, 파서는 이를 **"문자열을 닫는 따옴표"가
아니라 "따옴표 글자"로** 읽는다. 문자열이 안 닫힌 채 `,"ITM_ID"...`까지 이어지다가 결국
"여기 쉼표가 와야 하는데?"(`Expecting ','`)로 터진다.

`\"`는 A-2 표에 있는 **유효한 이스케이프**라, `\o`를 잡는 규칙(A-5)은 이걸 일부러 안
건드린다. 그래서 별도 규칙이 필요했다: **`\"` 바로 뒤에 구조 토큰(`,` `}` `]`)이 오면**
그 백슬래시를 종료 자리의 군더더기로 보고 `\\"`로 고친다(백슬래시는 리터럴, 따옴표는
종료자로 복원). 이 판별이 안전한 이유는, 값 안에 정상적으로 `",`를 포함한 문자열은
표준 파싱이 애초에 성공해 **이 교정(fallback)을 타지 않기** 때문이다.

> **교훈**: "JSON이 깨졌다"는 한 가지가 아니라 여러 형태일 수 있다. 표본(sample600)에는
> ①-b가 없어 1차 전수 크롤링에서야 드러났다. 관대 파서는 만나는 실제 깨짐 유형에 맞춰
> 규칙을 늘려가야 한다.
