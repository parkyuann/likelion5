## 0. 결론 세 줄

1. 현재 수집분은 **KOSIS 전체가 아니라 서비스뷰 하나(`MT_ZTITLE`, 국내통계 주제별)의 전체**다. 실측 확인된 서비스뷰는 **17개**(웹 노출 13 + API 전용 4)이고, 그중 **`MT_ZTITLE` 하나만** 수집했다. 7개 뷰는 수집률 0%다.
2. 실측으로 확인된 **미수집 표 최소 9,179건** + 작성중지통계(`MT_STOP_TITLE`, 177개 루트) 미측정분. 작성중지통계는 표본 1,215건 수집 시점에도 대기 노드가 371개 남아 있어 규모가 수만 건일 가능성이 있다.
3. 그와 별개로 크롤러에 **서브트리를 조용히 버리는 결함**이 있다. `list_tables()`가 API 오류를 예외가 아니라 dict로 반환하고, 크롤러는 그것을 `[WARN]` 한 줄만 찍고 건너뛴다 — 어느 노드가 유실됐는지 기록이 남지 않는다. 표본 6개 대분류를 재크롤해 보니 전부 재현됐으므로 대규모 유실 증거는 없지만, **검증할 방법 자체가 재크롤뿐**이고 전체의 60%를 차지하는 지역통계는 미검증이다.

#### vwCd 목록을 어떻게 확정했나 — 방법과 한계

세 가지 방법을 겹쳐서 썼다. **어느 하나도 단독으로는 완전성을 보장하지 못하기 때문**이다.

| 방법 | 내용 | 결과 |
|---|---|---|
| ① 웹 DOM 추출 | kosis.kr 좌측 메뉴의 `fnStatisticsList('...', 'MT_XXX', ...)` onclick 인자 전부 파싱 | **13개** — 웹 노출분에 대해서는 **완전** |
| ② 사이트 JS 스캔 | 로드된 스크립트 12개를 fetch해 `MT_[A-Z0-9_]+` 정규식 매칭 | 17개 문자열, 유효 코드는 ①과 동일 + `MT_ETITLE`. `MT_PTITLE`·`MT_ATITLE0x`는 **JS에도 없음** = 순수 API 전용 |
| ③ 네이밍 패턴 전수 탐색 | `MT_<A~Z>TITLE`, `MT_<A~Z>TITLE01~05`, `MT_TM<1~7>_TITLE` 등 **168개**를 `parentListId=""`로 호출, `err 30`이면 없음 / 리스트면 존재 | **17개 유효** |

세 방법의 합집합 = **17개**. ③에서 168개를 두드려 ①②가 못 찾은 `MT_PTITLE`·`MT_ATITLE01`·`MT_ATITLE02`를 건졌다.

> **남는 한계 (반드시 인지할 것)**: ③은 패턴을 벗어난 이름을 못 찾는다. 실제로 `MT_BUKHAN`·`MT_CHOSUN_TITLE`·`MT_HANKUK_TITLE`·`MT_STOP_TITLE`은 `MT_<문자>TITLE` 규칙 밖이며, ①에서 먼저 알았기 때문에 ③ 후보에 넣을 수 있었다. **같은 성격의 불규칙 이름이 웹에도 JS에도 안 나오는 채로 더 있을 가능성은 배제할 수 없다.**
>
> 확정하려면 KOSIS OpenAPI 매뉴얼(`openApi_manual_v1.0.pdf` — `kosis_client.get_meta()` 주석에 언급돼 있으나 레포에 파일 없음)의 `vwCd` 파라미터 표와 대조해야 한다. **P0에서 이 문서를 확보해 대조하는 것을 선행 작업으로 넣는다.**

성격도 서로 다르다 — 국제통계·북한통계·광복이전통계는 `MT_ZTITLE`과 **단 한 건도 겹치지 않는 독립 코퍼스**다. 뉴스 팩트체크에서 "북한 인구", "OECD 평균", "일제강점기 쌀 생산량" 류 주장이 들어오면 현재 카탈로그로는 **후보 표 자체가 존재하지 않는다**.

### 1.3 결함: 오류 응답을 표 없음으로 오해해 서브트리를 통째로 버림

`kosis_client.list_tables()`(`src/kosis_client.py:70-82`)는 `search_tables`/`get_data`/`get_meta`와 달리 **`err` 필드를 검사하지 않는다.** API가 `{"err":"40","errMsg":"호출가능건수를 초과..."}` 같은 dict를 돌려줘도 그대로 반환한다.

`kosis_tree_crawler.py:109-121`은 이걸 받아 `isinstance(items, list)`가 아니면 `[WARN]`만 출력하고 `continue` — **그 노드 아래 서브트리 전체가 큐에 들어가지 않고 사라진다.** 실패 노드 목록은 어디에도 저장되지 않아 사후 복구가 불가능하다.

실증(2026-08-09):

| 대분류 | 재시도 없이 재크롤 | 재시도 넣고 재크롤 | 저장된 값 |
|---|---|---|---|
| E 소득ㆍ소비ㆍ자산 | **81건** | 865건 | 865건 |
| I1 주거 | **331건** | 621건 | 608건 |

재시도만 넣으면 정확히 복원된다. 즉 유실은 데이터 문제가 아니라 **전적으로 이 결함 때문**이다.

그렇다면 최초 크롤 때도 유실이 있었는가 — 로그가 없어 직접 확인할 수 없으므로 **재시도를 넣고 대분류 6개를 다시 크롤해 대조**했다:

| 대분류 | 저장값 | 재크롤 | 신규 | 사라짐 | 복구실패 |
|---|---|---|---|---|---|
| E 소득ㆍ소비ㆍ자산 | 865 | 865 | 0 | 0 | 0 |
| M2 교통ㆍ물류 | 1,295 | 1,295 | 0 | 0 | 0 |
| L 광업ㆍ제조업 | 1,000 | 1,000 | 0 | 0 | 0 |
| K2 수산 | 929 | 929 | 0 | 0 | 0 |
| T 환경 | 1,002 | 1,002 | 0 | 0 | 0 |
| I1 주거 | 608 | 621 | **+13** | 0 | 0 |

**표본 6개는 전부 재현됐다** — 최초 크롤에서 대규모 유실이 있었다는 증거는 없다. 다만 이건 30개 중 6개, 그것도 작은 카테고리 표본이다. 호출 16,577회가 들어간 **지역통계(157,969건, 전체의 60%)는 확률적으로 가장 위험한 구간**이고, 검증도 재크롤 말고는 방법이 없다. 결함 수정(§3.1)과 재크롤(P6)을 둘 다 하는 이유다.

부수 확인: I1은 **13건이 늘었다(+2.1%, 약 2주 만에)**. KOSIS 목록은 계속 바뀌므로 **주기적 재크롤(드리프트 반영)도 설계에 넣어야 한다**.

## 3. 설계

### 3.1 `kosis_client.list_tables()` 수정 (선행, 필수)

```python
data = _loads_lenient(res.text)
if isinstance(data, dict) and "err" in data:
    if data["err"] == "30":      # 데이터 없음 = 정상적인 빈 노드
        return []
    raise RuntimeError(f"KOSIS API 오류: {data}")
return data
```

`err 30`(데이터 없음)만 빈 리스트로 흡수하고, 나머지(특히 `40` 분당 한도)는 예외로 올린다. 다른 함수들과 동작이 일치하게 된다.

> 기존 호출부 영향: `kosis_tree_crawler.py`는 이미 `try/except`로 감싸고 있어 예외가 WARN 경로로 들어간다. 아래 v2에서 그 경로를 "실패 노드 기록 + 재시도"로 바꾼다.

### 3.3 병합 규칙 — 경로는 뷰별로 전부 보존, 임베딩은 대표 경로 하나

키는 지금과 같이 `org_id:tbl_id`.

#### 현재 방식과 무엇이 다른가

`kosis_catalog_builder.py`는 지금 경로를 **뷰 구분 없이 한 리스트에** 모으고(`build_records()` 의 `paths[key].add(path)` → `sorted()`), `doc_meta_text`에는 **전부 ` ; ` 로 이어 붙인다**(`build_doc_meta_text()`).

```
# 101:DT_104Y258 실측
category_paths: [["국민계정","국가자산통계(구 국부통계)","국가자산통계(간접추계 신계열)"],
                 ["국민계정","국민대차대조표","2020년 기준","자산별 자본스톡"]]
doc_meta_text : 자산별 순자본스톡(명목, 연말기준) | 국민계정 > 국가자산통계(구 국부통계) >
                국가자산통계(간접추계 신계열) ; 국민계정 > 국민대차대조표 > 2020년 기준 >
                자산별 자본스톡 | 자산별            ← 76토큰
```

`MT_ZTITLE` 단일 뷰에서는 다중 경로 표가 **119건(0.04%)**뿐이라 무해했다. 그러나 경로가 1→2개가 되면 `doc_meta_text` 평균 토큰이 **56.7 → 102.6 (1.8배)** 로 뛴다.

뷰를 합치면 이게 전면화된다. 이번 부분 크롤만으로도 **8,493건**이 두 번째 경로를 얻는다(ATITLE01 5,377 · ATITLE02 1,968 · ETITLE 688 · PTITLE 460). 결정타는 `MT_OTITLE` — 국내통계를 기관 축으로 재배열한 뷰라 **거의 모든 표가 경로를 하나씩 더 갖는다.** 17개 뷰 전수면 표당 3~5개가 기본이 되어 임베딩 텍스트가 3배 이상 부푼다.

#### 결정 (2026-08-09)

**경로는 뷰별로 전부 남긴다.** 저장 비용은 JSONL이라 싸고, 어느 뷰에서 온 경로인지까지 보존해야 뷰별 필터링·감사가 가능하다. 대신 **임베딩 텍스트에는 대표 경로 하나만** 넣어 길이 폭증을 막는다.

```json
{"table_key": "101:DT_1DA7105S",
 "view_codes": ["MT_ZTITLE", "MT_OTITLE", "MT_PTITLE"],
 "category_paths": {
   "MT_ZTITLE": [["노동", "경제활동인구조사", "실업률"]],
   "MT_OTITLE": [["국가데이터처", "경제활동인구조사"]],
   "MT_PTITLE": [["경제활동인구조사"]]
 },
 "primary_view": "MT_ZTITLE",
 "primary_path": ["노동", "경제활동인구조사", "실업률"],
 "corpus": "domestic"}
```

| 층 | 무엇을 넣나 | 이유 |
|---|---|---|
| 저장 `category_paths` | **뷰별 dict, 전부** | 정보 손실 없음. 뷰별 필터·감사·재구성에 필요. 대표 아닌 경로도 여기에만 원본 보존 |
| 임베딩 `doc_meta_text` | **`primary_path` 하나만** | 길이가 검색 품질을 좌우 (`build_doc_meta_text` 주석: "짧게 유지하는 것이 목적") |
| BM25 `doc_item_index` | **항목명 + 차원값만** (v4와 동일) | 대표 아닌 경로 토큰은 넣지 않는다 (2026-08-12 결정, v4 동작 유지). 경로는 `category_paths` payload 로만 보존 |

`primary_view` 우선순위:

```
MT_ZTITLE > MT_STOP_TITLE > MT_RTITLE > MT_RTITLE01 > MT_BUKHAN
          > MT_CHOSUN_TITLE > MT_HANKUK_TITLE > MT_GTITLE01/02/03
```

큐레이션·재배열 뷰(`MT_PTITLE`·`MT_TM1/TM2`·`MT_ATITLE01/02`·`MT_ETITLE`)와 `MT_OTITLE`은 **대표 경로 후보에서 제외**한다 — 경로는 보존하되, `MT_OTITLE` 경로(`기관 > 조사 > …`)는 `org_name`·`stat_id`와 중복이라 대표로 쓸 가치가 없다.

> **미검증**: "경로를 다 넣으면 검색이 나빠진다"는 길이 기반 추론이지 측정 결과가 아니다. 현재 119건 사례로 A/B(대표 경로 1개 vs 전체 경로) 비교가 가능하므로, `reports/벡터DB_구성_개선안.md` 의 색인 그레뉴러리티 실험에 붙여 확인한다.

### 3.3.1 코퍼스 분리 — 컬렉션이 아니라 payload 필터로

뷰별로 컬렉션을 나누는 안을 검토했으나 **기각**한다. 17개 뷰는 배타적 분할이 아니라 같은 표를 재배열한 것이라, 컬렉션을 나누면 경로 중복이 **벡터 중복**으로 바뀐다 — 표당 벡터 3~5개, 임베딩 26만 → 80~130만 회, 전체 검색 시 N개 컬렉션 팬아웃과 점수 정규화 문제까지 생긴다.

대신 **의미상 배타적인 축은 코퍼스**다. 실측상 국제·북한·광복이전 통계는 `MT_ZTITLE`과 **중복 0건**이다.

| `corpus` | 구성 뷰 | 표 수 |
|---|---|---|
| `domestic` | ZTITLE ∪ OTITLE | 265,094+ |
| `discontinued` | STOP_TITLE | 미측정 |
| `international` | RTITLE, RTITLE01 | 2,839 |
| `north_korea` | BUKHAN | 997 |
| `pre1945` | CHOSUN, HANKUK | 3,411 |
| `local_indicator` | GTITLE01/02/03 | 363+ |

검색 의미론이 다르다 — "인구 몇 명"에 1930년 조선총독부 인구나 북한 인구가 섞이면 안 된다. 구현은 **컬렉션 1개 + `corpus` payload 인덱스 + 필터 검색**으로 한다(표당 벡터 1개 유지, 교차 검색은 필터만 제거).

```python
client.create_payload_index(collection_name="kosis_tables_v5",
                            field_name="corpus", field_schema="keyword")
```

`src/kosis_v2_indexer.py:226` 의 payload에 `corpus` · `view_codes` · `era` 를 추가하면 된다 — 구조 변경이 아니라 필드 추가다.

### 3.4 뷰별 색인 포함 여부 — 결정 필요

전부 벡터DB에 넣을 필요는 없다. 판단 기준은 "뉴스 팩트체크 후보로 검색돼야 하는가".

| 뷰 | 권고 | 근거 |
|---|---|---|
| ZTITLE / OTITLE / STOP / RTITLE / RTITLE01 / BUKHAN | **포함** | 현재/과거 국내·국제·북한 주장 검증에 직접 쓰임 |
| CHOSUN / HANKUK | **포함하되 `era: pre1945` 플래그** | 시대 맥락 없이 섞이면 오검색 위험 |
| GTITLE01/02/03 (e-지방지표) | **포함, `kind: indicator`** | 표가 아니라 가공 지표. 원표와 중복될 수 있음 |
| PTITLE / TM1 / TM2 / ATITLE01 / ATITLE02 | **미포함** (신규분만 흡수) | 84~97%가 ZTITLE 중복인 큐레이션·구분류 뷰 |
| ETITLE | **미포함** | 영문 미러 |
