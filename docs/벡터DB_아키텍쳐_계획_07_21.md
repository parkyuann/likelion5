# 벡터 DB 아키텍처 & 스키마·분류 고도화 계획

작성일: 2026-07-21 · 대상 단계: 실전2(통계표 매핑) → 최종(판정·설명)

---

## 0. 이 문서의 범위

1. 벡터 DB를 도입할 때 **전체 아키텍처를 어떻게 구성할지** — 무엇을 적재하고, 나중에 통계표와 어떻게 비교하는지
2. 그 검색 품질을 받쳐주기 위한 **스키마 구조 고도화 계획**
3. **모델(HCX)이 스키마에 맞게 잘 분류하도록 만드는 고도화 계획**

현재 코드에는 이미 벡터 DB를 전제한 흔적이 있다.
`retrieval_schema.py`의 `KOSISTable.document_text` / `embedding_model` / `embedding_version`,
`ClaimTableMapping.dense_score` / `sparse_score` / `reranker_score` 필드가 그것이다.
이 문서는 그 위에 구체 설계를 얹는다.

---

## 1. 핵심 원칙 — 벡터 DB는 "표 찾기"만 담당한다

가장 먼저 못 박아야 할 설계 결정이다.

- **벡터 DB의 역할** = 어떤 KOSIS 표를 봐야 하는가(**retrieval**)
- **벡터 DB가 하지 않는 것** = 수치가 맞는가(**verification**)

즉 벡터 DB에는 KOSIS **표의 메타데이터/설명 문서**를 적재하고(셀 값이 아님),
실제 수치 비교는 후보 표가 좁혀진 뒤 **KOSIS API로 그 표의 원자료를 실시간 조회**해서
결정론적 계산 모듈이 수행한다. 이는 readme의 원칙과 정확히 일치한다:

> "실제 수치 비교는 LLM이 아니라 결정론적 계산 모듈이 수행하며,
> 최종 설명은 공식 근거와 계산 결과 안에서만 생성"

**셀 값을 벡터로 넣지 않는 이유**
- 통계 수치는 (시점 × 차원 조합)으로 조회하는 구조화 데이터라 의미 유사도 검색 대상이 아니다.
- KOSIS 원자료는 갱신이 잦다. DB에 복제하면 낡은 값으로 오판할 위험이 생긴다.
- 검증 시점에 API로 직접 조회하면 "DB가 낡아서 틀리는" 문제가 원천적으로 사라진다.

## 2. 전체 아키텍처

```
[오프라인 색인 구축 — 배치, 가끔만 실행]

 kosis_table_tree.json  (크롤링 산출물, 약 95MB)
   └─ build_kosis_catalog.py
        └─ kosis_catalog_v1.jsonl   (표 1건 = 1레코드, org_id:tbl_id 단위)
             └─ [신규] 표 문서화 강화: tbl_name + 경로 + 차원명 + 항목명 + stat 설명
                  └─ [신규] kosis_indexer.py
                       ├─ HCX Embedding v2 → dense 벡터
                       ├─ BM25 → sparse 벡터
                       └─ metadata(org_id, period_type, 단위, 차원, version_status)
                            └─ Vector DB(Qdrant) 컬렉션에 upsert


[온라인 검증 — 기사/주장 1건 처리]

 Claim (스키마화 완료: convert_claim_listform_to_schema.py 산출물)
   │
   ├─[사전 필터]  claim_class == 집계통계  AND  source_scope == KOSIS등재 ?
   │        아니오 → 판단불가 확정, 조회 스킵 (비용 절약 + 오탐 방지)
   │        예 ↓
   │
   ├─ 질의문 생성: indicator_norm + population_norm + unit_norm + 시점
   │
   ├─ 하이브리드 검색
   │     ├─ Dense 검색 (top 50)     ─┐
   │     ├─ Sparse/BM25 검색 (top 50) ─┼─ 후보 병합
   │     └─ metadata 프리필터          ─┘  (org_id, period_type, 단위로 사전 배제)
   │          └─ Reranker(BGE) 재정렬 → top 5
   │               → ClaimTableMapping 레코드 생성 (dense/sparse/reranker_score 기록)
   │
   ├─ 표 선택 → KOSIS 자료 API로 해당 (표, 항목, 시점, 차원조합) 셀 조회
   │
   ├─ 결정론적 비교 모듈
   │     ├─ change_type별 계산 (증감률 / 증감폭 / 순위 / 단순수치)
   │     ├─ 근사 오차 규칙 ("3명 중 1명" ≈ 실측 35.5% 를 허용 범위 내면 통과)
   │     └─ 결과 → list_alignment_status (ALIGNED / COUNT_MISMATCH / LOW_CONFIDENCE …)
   │
   └─ 근거 인용형 설명 생성 (RAG)
         → 확정된 수치·시점·출처만 프롬프트에 투입, 근거 밖 생성 차단
```

## 3. 벡터 DB에 무엇을 적재하나 (색인 단위 = 표 1개)

`build_kosis_catalog.py`는 이미 `table_key = org_id:tbl_id` 단위로 정규화하고
`document_text`를 만든다. 다만 현재 `document_text`는
`tbl_name + org_id + stat_id + 경로`뿐이라 **차원명·항목명이 빠져 있다.**
검색 품질의 핵심이 여기라 반드시 보강해야 한다(§4 참조).

레코드 예시(Qdrant 포인트 1개):

```jsonc
{
  "id": "101:DT_1DA7001",
  "dense_vector":  [ ... ],          // 강화된 document_text의 HCX 임베딩
  "sparse_vector": { "성별": 0.4, "연령계층": 0.5, ... },  // BM25
  "payload": {                        // = metadata, 필터·표시용
    "table_key":   "101:DT_1DA7001",
    "org_id": "101", "org_name": "국가데이터처",
    "tbl_name": "성/연령별 경제활동인구",
    "category_path": ["고용·노동·임금", "경제활동인구조사"],
    "period_types": ["M", "Q", "Y"],    // 시점 필터
    "dimensions": ["성별", "연령계층", "취업/실업"],
    "units": ["천 명", "%"],
    "version_status": "current"         // 시기별로 갈라진 표 구분(데이터 특성 #4)
  }
}
```

### 왜 Dense + Sparse 둘 다인가

readme의 데이터 특성 #2가 근거다.
"물가" 하나가 소비자물가/생산자물가/농가판매및구입가격조사로 갈라지고,
뉴스가 "쌀값"이라고만 쓰면 산지가격인지 소비자가격인지부터 판별해야 표를 특정할 수 있다.

- **Dense(임베딩)**: 뉴스 표현 ↔ 표 이름의 **의미 유사도**를 잡는다 ("취업자 수" ↔ "경제활동인구").
- **Sparse(BM25)**: 정확한 통계 **용어 일치**를 잡는다 (희귀 지표명·기관명이 그대로 나올 때 강함).

스키마의 `dense_score` / `sparse_score` 필드가 바로 이 두 점수를 저장하려던 자리다.

## 4. 통계표와의 비교는 어떻게 하나

후보 표가 top 5로 좁혀진 다음이 진짜 검증 단계다.
이건 벡터 유사도가 아니라 **구조적 정렬 + 결정론적 수치 비교**다.

1. **차원 정렬** — Claim의 `population_norm`("60세 이상"), `time_start`, `unit_norm`을
   표의 dimension 값에 매핑한다 → `ClaimTableMapping.matched_dimensions`.
   정렬 실패/모호는 `list_alignment_status = COUNT_MISMATCH / LOW_CONFIDENCE`로 남긴다.
2. **셀 조회** — 정렬된 (표, 항목ID, 시점, 차원조합)으로 KOSIS 자료 API를 호출해
   실제 수치를 확보한다. (DB의 복제본이 아니라 원본을 본다)
3. **결정론적 비교**
   - `change_type`별 계산: 증감률 / 증감폭 / 순위 / 비교 / 단순수치
   - **근사 오차 규칙**: 반올림식 서술의 허용 오차를 판정 로직에 명시
     (예: "60세 이상 3명 중 1명" = 33.3% 서술, 실측 35.5% → 허용 범위 내면 ALIGNED)
   - 결과 → `list_alignment_status` (ALIGNED / COUNT_MISMATCH / …)
4. **근거 인용형 설명** — 확정된 수치·시점·출처만 프롬프트에 넣어
   "어떤 표의 어떤 값을 근거로 판정했는지" 명시. 근거 밖 정보 생성 차단.

**판단불가의 두 원인을 구분해서 로깅**한다(readme 인사이트 반영):
- `NO_KOSIS_MATCH` + KOSIS 내부에 표는 있으나 못 찾음 → 검색 개선 여지 (실전2 대상)
- KOSIS 자체에 데이터 없음 → 프로젝트 범위 밖, 개선 불가로 명시

## 5. 벡터 DB 선택

| 후보 | 평가 |
| --- | --- |
| **Qdrant (추천)** | 로컬 도커·경량. Dense+Sparse 하이브리드 네이티브 지원. metadata 필터 강력. 표 수만~수십만 규모에 오버스펙 없이 적합 |
| Weaviate | 기능 충분하나 무겁고 스키마 관리 부담 |
| pgvector | 이미 Postgres를 쓰면 이점. 단 sparse 하이브리드가 약함 |
| FAISS | 순수 라이브러리. metadata 필터·sparse를 직접 구현해야 해 현 단계엔 비추 |

`kosis_catalog_v1.jsonl` 규모(수만 건 추정)면 **Qdrant 단일 컬렉션 하나**로 충분하다.

## 6. 기존 코드와의 접점 (새로 만들 것)

| 작업 | 대상 | 내용 |
| --- | --- | --- |
| 문서화 강화 | `build_kosis_catalog.py` | `document_text`에 **차원명·항목명** 추가 (현재 누락) |
| 색인기 | (신규) `kosis_indexer.py` | catalog jsonl → HCX 임베딩 + BM25 → Qdrant upsert |
| 검색기 | (신규) `kosis_retriever.py` | Claim → 하이브리드 검색 + 리랭커 → `ClaimTableMapping` 반환 |
| 리랭커 | `retrieval_schema.py` `reranker_score` | 자리는 있으나 모델 미연결. HCX엔 전용 리랭커 API가 없어 **BGE-reranker-v2-m3** 오픈 모델을 로컬로 붙이는 게 현실적 |
| 의존성 | `requirements.txt` | `qdrant-client`, 리랭커용 `FlagEmbedding` 또는 `sentence-transformers` 추가 |

> 참고: `hcx_embedding_client.py`의 임베딩 차원 수를 먼저 확인해 Qdrant 컬렉션의 vector size로 맞춰야 한다.

## 7. 스키마 구조 고도화 계획

검색·판정 품질은 결국 **Claim 스키마가 얼마나 매핑에 친화적인가**로 갈린다.
`retrieval_schema.py`의 현 구조를 다음 방향으로 손본다.

### 7-1. 정규화 필드를 매핑 키로 승격
- `indicator_norm`, `population_norm`, `unit_norm`이 지금은 자유 텍스트에 가깝다.
  이를 **통제 어휘(controlled vocabulary)**로 수렴시킨다.
  - 지표 사전: 뉴스 표현 → KOSIS 지표군 매핑표 (예: "쌀값" → {산지쌀값, 소비자물가:쌀})
  - 행정구역·단위는 이미 `claim_normalizer.py`가 다루므로 그 산출을 스키마 필드에 고정.
- 효과: 질의문 생성과 metadata 프리필터가 문자열 운에 덜 의존하게 된다.

### 7-2. observations 단위 구조 확정 (나열형 문장 대응)
- readme의 구조적 이슈: "문장 1개 = 클레임 1개" 가정이
  "17만1000명, 16만6000명, 31만2000명…" 같은 나열형에서 깨진다.
- 이미 `ClaimObservation`(value/period/dimension/sequence)이 있으니,
  **추출기가 문장 단위가 아니라 수치 토큰 단위로 observation을 채우도록** 계약을 못 박는다.
- `relation_type`(time_series / ranked_list / part_whole …)을 필수로 강제해
  비교 모듈이 계산식을 결정할 수 있게 한다.

### 7-3. 사전 필터 3필드의 판정 경로 분리
- `claim_class`(LLM), `source_scope`(코드 사전), `verifiability_prefilter`(파생)
  세 필드의 책임을 문서에 명시.
- `source_scope`는 이미 `source_scope_classifier.py`가 181개 기관 사전으로
  **결정론적으로** 판정한다(LLM은 원문 기관명만 추출). 이 "LLM은 추출만, 판정은 코드" 패턴을
  다른 축에도 확대 적용할지 검토한다(예: 단위 정규화, 시점 파싱).

### 7-4. 매핑 결과의 실패 사유 코드화
- `ClaimTableMapping.filter_reason`, `status`(NO_KOSIS_MATCH 등)와
  `list_alignment_status`를 조합해 **판단불가 사유를 기계 판독 가능하게** 남긴다.
  → 실전2 검색 개선 대상과 범위 밖(구조적 불가)을 자동 집계할 수 있다.

## 8. 모델(HCX)의 스키마 분류 정확도 고도화 계획

현재 추출은 `hcx_claim_experiment.py`의 `SYSTEM_PROMPT` + JSON 스키마로 이뤄진다.
분류 정확도를 끌어올리는 순서는 다음과 같다.

### 8-1. gold 라벨 기반 오류 진단 (선행 필수)
- 이미 있는 자산: `data/labeling/`의 team1·team2 gold 라벨(기사·후보 단위).
- 먼저 **혼동행렬**부터 그린다. 특히 다음 경계가 자주 틀린다:
  - 집계통계 ↔ 개별사례 (모집단 단위 여부)
  - 집계통계 ↔ 사고대응임시통계 (국정자원 화재 복구율 같은 일회성 집계)
  - 해석수사(과장 표현) ↔ 실제 주장
- 어느 경계에서 얼마나 틀리는지를 **수치로 확정**한 뒤에야 프롬프트를 손댄다.
  (지금은 "약 25~30%가 검증시도" 수준의 관측만 있음)

### 8-2. 모델 매트릭스 비교로 기준 모델 확정
- `hcx_claim_experiment_matrix.py`가 이미 5종(HCX-003/005/007/DASH-001/002)을 돌린다.
- 동일 gold 표본에 대해 claim_class **정확도 / F1**을 모델별로 비교해 기준 모델을 정한다.
- `HCX-007`만 `responseFormat`(JSON 스키마 강제)을 지원한다는 점이 스키마 준수율에서
  유리할 수 있으니, "분류 정확도" 외에 "스키마 파싱 실패율"도 함께 지표화한다.

### 8-3. 프롬프트 고도화 (진단 결과에 맞춰서만)
- **정의 경계 명문화**: claim_class 9종 각각에 "포함/제외" 예시를 프롬프트에 넣는다.
  특히 "모집단 단위 집계통계만 인정" 규칙(개인·순위·시세·전망·정책목표·제도기준 제외)을
  라벨링 기준과 100% 일치시킨다.
- **Few-shot**: 8-1에서 발견한 오분류 경계에 대해 대표 예시 2~3개씩 프롬프트에 삽입.
- **책임 분리 유지**: source_scope는 LLM에게 맡기지 않는다(코드 사전 판정 유지).
  프롬프트는 `source_org_raw` 원문 추출 정확도에만 집중.

### 8-4. 후처리 검증 게이트 추가
- LLM 출력 → `retrieval_schema.py`의 `validate_claim()`으로 **스키마 위반 자동 차단**.
  (value_num 있는데 unit_norm 없음, time_start > time_end 등)
- 위반 행은 재요청 또는 규칙 기반 보정으로 회수하고, 회수율을 지표로 관리.

### 8-5. 평가 지표 설계
| 지표 | 정의 | 자산 |
| --- | --- | --- |
| claim_class 정확도/F1 | gold 대비 클래스 일치 | `data/labeling/*` |

## 9. 권장 착수 순서
