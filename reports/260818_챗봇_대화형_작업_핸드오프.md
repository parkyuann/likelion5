# 대화형 챗봇 전환 — 작업 핸드오프

작성일: 2026-08-18 · 브랜치: `hyeonseo` · 도식: [`reports/260817_챗봇_대화형_아키텍처.html`](260817_챗봇_대화형_아키텍처.html)

> **이 문서의 목적**: 기존 KOSIS 팩트체크 파이프라인을 클로드/GPT 같은 **대화형 챗봇**으로 전환하는 작업의 확정 설계·현재 상태·다음 할 일을 다음 세션에 넘김. 설계 논의는 끝났고, 이제 구현 단계.

---

## 1. 무엇을 만드는가

- 기존: 기사 원문 하나 넣으면 → 문장별 팩트체크 결과 (단발성)
- 목표: **대화가 이어지는 챗봇** — 기사 검증 + 후속질문 + 일반 질의 + 이미지/URL 입력
- 담당 분담: **hyeonseo = 프론트 + 대화 계층(코드판별·오케스트레이터·캐시즉답·세션저장소)** / **팀원 = 분석 파이프라인·MCP·백엔드 서버**

---

## 2. 확정 아키텍처 (2단 라우팅)

```
사용자 입력
   │
[코드 판별]  ← 이미지 첨부? URL? (결정적, LLM 아님 · 백엔드)
   ├─ 이미지 → HCX-005 인식 → 분석 파이프라인
   ├─ URL   → 텍스트 추출(방식 미정) → 분석 파이프라인
   └─ 텍스트 → [오케스트레이터 HCX-DASH-002 + function calling]
                 ├─ 기사텍스트 → 분석 파이프라인
                 ├─ 후속형    → 캐시 즉답 (파이프라인 재실행 X)
                 └─ 질의      → MCP
분석 파이프라인 = 검색 → 리랭커 → RAG reasoning 판정
   │
최종 답변 → 프론트
```

**모델·기술 배치 (중요)**

| 단계 | 담당 | RAG reasoning |
|------|------|:---:|
| 코드 판별(이미지/URL) | 코드 | ❌ (LLM 자체가 아님) |
| 텍스트 분류(기사/후속/질의) | HCX-DASH-002 + FC | ❌ |
| 이미지 → 텍스트 | HCX-005 | — |
| 최종 판정 | **HCX rag-reasoning** | ✅ **여기 한 곳만** |

- **라우팅에 RAG reasoning(모델이든 `rag-reasoning` 엔드포인트든) 절대 안 씀.** 라우터는 경량(DASH-002).
- function calling 지원 모델: HCX-005 / HCX-DASH-002 / HCX-007만. **HCX-DASH-001·HCX-003은 미지원.**
- HCX 제약: function calling과 이미지입력·structured output·thinking은 **한 요청에 동시 사용 불가** → 이미지는 (비전 추출)+(분석) 2단 분리.

## 3. 세션 저장소 (대화 맥락의 핵심)

`session_id` 하나로 묶이는 두 가지:

| | 히스토리 | 근거 캐시 |
|--|----------|-----------|
| 담김 | 사용자 발화 + 봇 답변 텍스트 | 후보5 · 판정 · 추출된 기사 원문 |
| 저장 시점 | 매 턴 | 파이프라인 돌 때(새 기사일 때만) |
| 저장 주체 | 답변 | 분석 파이프라인 |
| 용도 | 대화 맥락 유지 | 후속질문에 근거로 답 |

- **재질의 구분**: 새 분석대상(이미지/URL/기사텍스트) 있으면 신규, 짧은 텍스트+이전 참조면 후속형. 이미지 origin은 분석 후 텍스트로 세션에 남으므로 후속 판단은 origin 무관.
- 기사 비교·과거 기사 되돌아감 **없음** → 캐시 슬롯 **1개 덮어쓰기**로 충분.
- 세션 수명: `session_id`를 저장 안 하면 재접속 시 리셋(현재 방침). Redis TTL로도 만료. 여러 사용자 격리는 자동.

## 4. 현재 상태

- **프론트**: React+Vite, 채팅 UI 뼈대 **이미 있음**(`frontend/src/ChatApp.jsx`). 아직 mock 데이터.
  - 잘 돼 있는 것: 말풍선 리스트, 입력창, **응답 2종 렌더**(`article` 문장별 판정 / `text` 일반 말풍선) — 우리 설계와 그대로 맞음.
  - **문제**: `handleSend`(ChatApp.jsx:365)가 모든 입력을 무조건 기사 검증(`runVerify`→`mockAnalyze`)으로 처리함. 대화형에선 프론트가 분류하면 안 됨.
- **백엔드 서버**: 아직 없음(팀원 작업). 파이프라인 끝단 = `src/ncp_rerank_reasoning_chain.py`.

## 5. 다음 할 일

### 프론트 (우선순위 높음)
1. **`session_id` 추가** — 페이지 로드 때 1회 생성(`crypto.randomUUID()`), 매 메시지에 실어 전송. (지금 아예 없음)
2. **`handleSend` 리팩터링** — "무조건 분석"에서 → "전송 후 응답 종류대로 렌더"로. 프론트는 분류하지 않고 `{session_id, text, image?}` 보내고, 응답의 `type`으로 분기.
   - 렌더 컴포넌트(`ArticleResult`, text 말풍선)는 이미 있으니 재사용.
   - mock·DEMO·진행 애니메이션은 "분석 응답" 스텐드인으로 당분간 유지 OK.
3. **입력 담기** — 이미지 붙여넣기는 텍스트 아닌 **첨부 필드**로 분리해 전송(나중 단계).

### 요청/응답 계약 (팀원과 맞출 것)
```
요청:  { session_id, text, image? }
응답:  { type: "analysis", segments: [...] }   // 문장별 (frontend/HANDOFF.md §6 배열)
   또는 { type: "answer",   text: "..." }        // 캐시즉답 / 질의
```

### 백엔드 대화 계층 (hyeonseo)
- 코드 판별(이미지 필드 유무 / URL 정규식) → 오케스트레이터 앞단, **백엔드에 위치**(프론트 아님).
- 오케스트레이터: HCX-DASH-002 chat-completions + function calling. 도구는 우선 `analyze_article` 하나.
- 캐시 즉답: 후속형이면 파이프라인 안 돌리고 세션 근거+히스토리로 답.
- 세션 저장소: **Redis 접근을 함수로 감싸기**(로컬 dict ↔ Redis 교체 쉽게).

## 6. AWS 배포 체크리스트

배포 구성: 앱=ECS/Fargate·EC2 / Qdrant=EC2·ECS+EBS / Redis=ElastiCache / 키=Secrets Manager / 서울 리전(ap-northeast-2).

**설계 방향은 AWS 배포에 맞음** ✅ (무상태 앱 + 외부 세션 + Qdrant/Redis 분리). 단, 실제 구현에서 아래를 맞게 지어야 함:

- [ ] **세션을 인메모리 dict로 두지 말 것** → Redis. (다중 인스턴스에서 후속질문 깨짐) ★최우선
- [ ] **파이프라인 파일 I/O 제거** — `ncp_rerank_reasoning_chain.py`가 결과를 `mapping_records.jsonl`에 쓰고 카탈로그를 로컬 파일에서 읽음. 서비스화 시 결과는 응답+세션으로만, 카탈로그는 이미지에 굽거나 S3/DB 등 지속 소스에서 로드. ★최우선
- [ ] **긴 파이프라인 타임아웃** — HCX 다중 호출로 수십 초 가능. ALB idle(기본 60s)·API Gateway(29s) 주의 → SSE 스트리밍 또는 비동기 큐 권장.
- [ ] **MCP 서버 호스팅 위치** 결정.
- [ ] **쿼리 임베딩 GPU 여부** — HCX 임베딩 API면 GPU 불필요, BGE 직접 서빙이면 GPU 필요(비용 직결).

## 7. 미정 항목

- URL 텍스트 추출 방식: 정적 크롤링(requests+BeautifulSoup) vs 헤드리스 브라우저(Playwright, JS 렌더링 언론사 대비).
- 쿼리 임베딩: BGE 직접 서빙 vs HCX 임베딩 API(`src/hcx_embedding_client.py`).
- MCP 서버 용도: KOSIS 검색용 vs 일반 답변용 (팀원 확인 필요).
- 재접속 시 대화 이어가기 여부(현재는 리셋 방침).
