# HCX 모델 Structured Output 비교 실험 보고서

## 1. 실험 개요

- **목적**: (1) HCX-007에서 structured output 사용/미사용 효과 비교, (2) 전체 HCX 계열 모델 주장추출 성능 비교
- **데이터**: `data/evaluation/pilot120.csv` (120건, gold 라벨 포함)
- **공통 조건**: `temperature=0.0`, `top_p=0.8`, **동일한 system 프롬프트**(원본 프롬프트, 라벨 목록 미포함)
- **평가**: gold 대비 exact-match 기반 지표 (`calculate_metrics`)

|---|---|---|---|---|---|

## 3. 핵심 발견

### 3-1. Structured output의 효과 = "주장탐지 소폭↑ + 형식 100% 보장, 대가는 토큰↑" (케이스 5 vs 6)

thinking을 양쪽 다 끄고 HCX-007만 structured output on/off로 비교하면:

| | 5. SO off | 6. SO on | 차이 |
|---|---:|---:|---|
| 주장탐지 F1 | 0.928 | **0.954** | SO on 소폭 우위 |
| Recall | 0.866 | **0.912** | SO on 우위 |
| 형식 실패 | 1건 | **0건** | SO on이 완벽 보장 |
| 평균 토큰 | **441** | 631 | SO on **+43%** |
| 비용(120건) | **151.3원** | 172.2원 | SO on **+14%** |
| RLT | **0.727** | 0.721 | 사실상 동률 |

→ structured output은 **주장탐지 성능을 약간 올리고 출력 형식을 100% 보장**하지만, 스키마 강제 오버헤드로 **토큰을 43% 더 쓴다**(비용은 +14% — 늘어난 토큰이 대부분 저렴한 입력 토큰이라 §6). HCX-007은 프롬프트만으로도 스키마를 잘 지켜(실패 1건) 두 방식이 근접하므로, **형식 보장이 절대적으로 필요한 경우가 아니면 프롬프트-only도 유력한(더 저렴한) 대안**이다.

### 3-2. 모델별 주장탐지 성능 (프롬프트-only 공정 비교, 케이스 1~5)

동일 조건(프롬프트만) 하에서:

- **HCX-DASH-002 = 종합 가성비 최고**: F1 0.986, 가장 빠름(1.1초), 최소 토큰(307), 실패 1건, **RLT 0.851 최고**.
- **HCX-DASH-001**: F1 0.995로 탐지 최고지만 느리고(4.4초) 형식 실패 12건.
- **HCX-007 (SO off)**: F1 0.928로 안정적, 형식 실패 1건.
- **HCX-003**(베이스라인): F1 0.891로 약하고 느림(5.7초).
- **HCX-005**: 스키마 미준수로 사실상 사용 불가(§3-3).

### 3-3. HCX-005의 스키마 붕괴 — structured output이 필요한 이유

HCX-005는 프롬프트로 스키마를 지시해도 **자기 방식대로 `claims` 배열로 감싼 JSON**을 반환했다. `is_claim`이 최상위에 없어 116건 중 105건이 "주장 아님"으로 처리 → recall 0.101, **F1 0.183**. 이는 모델의 탐지력 부족이 아니라 **지시된 출력 스키마를 따르지 않은 결과**로, structured output(형식 강제)이 필요한 이유를 직접 증명한다. (같은 프롬프트에서 HCX-007은 잘 지킨 것과 대조적 — 형식 준수는 모델 의존적.)

## 4. 방법론 및 지표 해석 주의사항

### 4-1. HCX-007 프롬프트-only는 thinking을 반드시 꺼야 공정하다

HCX-007에서 responseFormat만 단순히 제거하면 **thinking(추론)이 켜진 채로 남는다**(원본 코드에서 `thinking={"effort":"none"}`이 responseFormat 블록 안에 있기 때문). thinking이 켜진 상태로 돌리면 추론이 `maxCompletionTokens`를 소진해 **120건 중 55건이 "content empty"로 실패**하고, 지연 20.9초·토큰 1589로 폭증한다. 이는 structured output 제거 효과가 아니라 thinking의 부수효과이므로, 본 보고서의 케이스 5는 **thinking을 명시적으로 끈 전용 실행 파일**(`hcx_claim_experiment_noso_nothink.py`)로 측정해 케이스 6과 thinking 조건을 일치시켰다.

아래는 이 교란을 보여주는 HCX-007 3종 실측이다. A-1차와 A-2차는 **똑같이 structured OFF**이고 **thinking만 다른데**, thinking을 끄자 실패 55→1건·지연 20.9→3.3초·토큰 1589→441로 정상화된다 — 1차의 처참한 수치가 structured output이 아니라 thinking 탓이었음을 확인시킨다.

| 007 케이스 | structured | thinking | 성공/실패 | F1 | Recall | 평균지연 | 평균토큰 | RLT |
|---|---|---|---:|---:|---:|---:|---:|---:|
| A-1차 (오염) | OFF | **ON** | 65 / 55 | 0.927 † | 0.864 | 20.9초 | 1589 | 0.496 |
| A-2차 (본문 케이스 5) | OFF | OFF | 119 / 1 | 0.928 | 0.866 | 3.3초 | 441 | 0.727 |
| B (본문 케이스 6) | **ON** | OFF | 120 / 0 | 0.954 | 0.912 | 3.3초 | 631 | 0.721 |

† A-1차 F1은 성공 65건만 기준(생존편향)이라 120건 기준 A-2차·B와 직접 비교 불가.

### 4-2. claim_class / source_scope = 전부 0.0 (측정 불가)

6개 케이스 모두 이 두 지표가 0.0이다. 원인은 **라벨 공간 불일치**: gold는 한글 고정 분류표(`집계통계` 등)인데, 이 실험들은 **enum 제약을 쓰지 않아** 모델이 `numeric`·`economic` 등 자유 라벨을 생성했기 때문이다. 따라서 이 두 지표는 본 비교에서 변별력이 없다. 해결책(스키마 enum)은 **부록 A** 참조.

### 4-3. source_role_exact 참고

전 케이스 0.81~0.93로 높지만, gold의 다수가 빈값이라 "빈값=빈값"으로 부풀려진 값이라 변별력이 낮다.

## 5. 결론 및 권고

1. **structured output(케이스 6)은 형식 안정성에서 최고**(실패 0/120, 스키마 100% 준수)이고 주장탐지도 소폭 우위. 파이프라인 신뢰성이 중요하면 이 방식이 사실상 필수.
2. 단, HCX-007은 **프롬프트-only(thinking off)도 거의 대등**(F1 0.928, 실패 1건)하면서 토큰을 43% 아끼므로, 비용 민감 상황의 대안이 된다.
3. **프롬프트-only 모델 중에서는 HCX-DASH-002가 가성비 최고**(빠르고 저토큰·고안정·RLT 최고).
4. **HCX-005는 프롬프트-only로는 부적합**(스키마 미준수).
5. **claim_class/source_scope를 유의미하게 측정하려면 enum 필수**(부록 A). 향후 전 모델에 enum 적용 시 분류 성능까지 비교 가능.

## 부록 A. enum 스키마 보조 실험 (HCX-007, 별개)

`claim_class`/`source_scope`의 0.0 문제를 검증하기 위해, `CLAIM_SCHEMA`에 허용 라벨을 `enum`으로 강제한 `hcx_claim_experiment_enum.py`로 HCX-007을 별도 실험했다(50건).

| 지표 | enum 미적용 | enum 적용 |
|---|---:|---:|
| claim_class_accuracy | 0.00 | **0.26** |
| source_scope_exact | 0.00 | **0.08** |
| 평균 토큰 | 624 | 951 (+52%) |

→ enum은 예측을 gold와 같은 라벨 집합으로 강제해 **인위적 0값을 해소**하고 분류 성능을 측정 가능하게 만든다(토큰 비용은 증가). 측정된 26%는 모델이 "집계통계↔개별사례"를 자주 혼동하는 실제 약점을 드러낸다.
