## 1. ① `kosis_tree_crawler.py` — 표 목록 만들기

### 1.1 하는 일

30개 대분류(A~V)를 큐에 넣고 BFS로 내려간다. `list_tables(parent_id)` 응답 원소가 두 종류다.

- `LIST_ID` 있음 → 중간 카테고리. 큐에 넣고 이름을 `path`에 이어붙인다.
- `TBL_ID` 있음 → 리프(통계표). `org_id / tbl_id / tbl_nm / stat_id / path`를 저장한다.

대분류 하나가 끝날 때마다 JSON 전체를 다시 쓰므로(`kosis_tree_crawler.py:186`) **대분류 단위**로는
중단·재개가 된다.

### 1.2 문제

#### (1-a) 호출 속도가 KOSIS 한도를 2배 초과한다 — 실제 버그

`SLEEP_SEC = 0.15`(`:28`)는 분당 **400회**다. KOSIS 한도는 분당 200회(에러코드 40)이고,
②의 enricher는 이를 알고 `MAX_CALLS_PER_MIN = 180`을 쓴다(`kosis_meta_enricher.py:64`).
같은 API 키를 쓰는 두 스크립트가 서로 다른 가정을 하고 있다. 한도는 **키 단위 합산**이므로
재크롤링하면 절반이 코드 40으로 떨어진다.

> 조치: `SLEEP_SEC` 0.15 → **0.34** (분당 176회). 재크롤링 전 필수.

#### (1-b) 실패한 노드가 기록되지 않는다 — 완전성을 증명할 수 없는 구조

```python
except Exception as e:
    print(f"    [WARN] {parent} 조회 실패: {e}", flush=True)
    ...
    continue          # 재시도 없음, 실패 목록에 남기지도 않음
```
(`:94-106`)

`list_tables`에는 재시도가 없다(`timeout=10`, 1회 시도). 중간 카테고리 하나가 타임아웃되면
**그 아래 서브트리 전체가 통째로 사라지고** 흔적은 stdout WARN 한 줄뿐이다. 노드마다 진행률을
출력하므로(`print_progress`) 26만 줄 넘는 로그에서 이를 찾을 수 없고, 예외 경로는 `time.sleep`을
건너뛰므로 장애 시 백오프 없이 더 빠르게 두드린다.

문제의 본질은 **`kosis_table_tree.json`만 보고는 크롤이 완전했는지 판정할 수 없다**는 것이다.
파일에 저장되는 카테고리별 필드는 `top_id / top_nm / leaf_count / calls / leaves`뿐이고,
시도 횟수·실패 수가 없다. 실패한 노드는 `calls`에도 잡히지 않고 `leaves`에도 없으므로
**파일 안에서 흔적이 0이다.** → 실제 검증은 §1.3 참조.

> 조치: `failed_nodes.jsonl`에 실패 노드를 기록하고, 크롤 종료 후 재시도 패스를 돌린다.
> 카테고리별로 `processed_nodes` / `failed_nodes` / `empty_nodes`를 함께 저장한다.

#### (1-c) 방문 집합(visited)이 없다

같은 `LIST_ID`가 두 부모 아래 노출되면 중복 순회하고, 순환이 있으면 무한 루프다. 실측 중복은
119건(265,213 → 265,094)으로 피해는 작지만 안전장치가 없다.

#### (1-d) 응답에 있는 필드를 버린다 — 비싼 누락

리프 응답 실측:

```json
{"STAT_ID":"2008001","SEND_DE":"2026-07-02","TBL_ID":"DT_1B040B3",
 "REC_TBL_SE":"N","ORG_ID":"101","TBL_NM":"행정구역(시군구)별 주민등록세대수"}
```

`SEND_DE`(자료갱신일)는 공짜로 얻는 신선도 신호인데 `:126-132`에서 저장하지 않는다.
`REC_TBL_SE`(추천표 여부)도 버린다. 나중에 넣으려면 26만 표를 재크롤링해야 한다(②는 61시간).

> 조치: 다음 전량 크롤링 기회에 `SEND_DE`·`REC_TBL_SE`를 반드시 포함.

#### (1-e) 트리 저장이 원자적이지 않다

②는 temp→replace를 쓰는데(`kosis_meta_enricher.py:208`) ①은 100 MB JSON을 그대로 덮어쓴다.
쓰는 중 죽으면 트리 전체가 깨진다.

### 1.3 트리 완전성 검증 — 실제로 손실이 있었는가

(1-b)는 "검증 수단이 없다"는 **구조적 결함**이지 "손실이 있었다"는 판정이 아니다. 그래서
별도로 검증했다. **결론: 손실 증거를 찾지 못했다.** 단 검증 커버리지는 전체의 약 24%다.

#### 검증 1 — 작은 대분류 5개 전량 재크롤 후 대조 (결정적)

재시도 3회·분당 176회·실패 전량 기록으로 독립 재크롤해 `org_id:tbl_id` 집합을 비교했다.

| 대분류 | 기존 표 | 재크롤 표 | 기존 `calls` | 재크롤 노드 | 원 크롤 누락 | 재크롤 실패 |
|---|---|---|---|---|---|---|
| P2 물가 | 51 | 51 | 13 | 13 | **0** | 0 |
| P1 임금 | 113 | 113 | 20 | 20 | **0** | 0 |
| I1 주거 | 608 | 608 | 59 | 59 | **0** | 0 |
| K2 수산 | 929 | 929 | 67 | 67 | **0** | 0 |
| T 환경 | 1,002 | 1,002 | 70 | 69 + 빈노드 1 | **0** | 0 |
| **합** | **2,703** | **2,703** | 229 | 229 | **0** | 0 |

표 집합이 완전히 일치하고, **`calls` 수까지 정확히 맞는다.**

여기서 실용적인 발견이 하나 나왔다. 원 크롤러는 `calls += 1`을 `isinstance(items, list)` 검사
**앞에서** 하므로(`:107` vs `:109`), `calls`는 "예외 없이 응답을 받은 노드 수"이고
`err:30`(빈 노드)도 포함한다. 반면 예외 실패는 제외된다. 따라서:

> **`calls` ≟ 깨끗한 재크롤의 노드 수** 가 예외 실패를 정확히 탐지하는 지표다.
> T에서 70 = 69(정상) + 1(`err:30`)로 딱 맞은 것이 이 해석을 검증한다.

#### 검증 2 — 지역통계(V) 상위 구조를 KOSIS에 직접 재조회

형제 규칙성 검사는 '있는 노드끼리' 비교하므로 **지자체가 통째로 유실되면 탐지할 수 없다.**
그 사각지대를 메우려고 API에서 목록을 직접 받아 대조했다.

| 계층 | API | 트리 | 차이 |
|---|---|---|---|
| V 직계 자식 | 4 | 4 | 없음 |
| 지자체 기본통계 > 광역 | 16 | 16 | 없음 |
| 광역 > 지자체 단위 | **216** | **192** | **24곳이 트리에 없음** |

24곳(서울 자치구 23 + 경기도 연천군)을 유실로 의심해 3곳을 실제로 내려가 봤다.

```
서울강남구  201_201A_523_52302 → {"err":"30","errMsg":"데이터가 존재하지 않습니다."}
서울강동구  201_201A_525_52501 → {"err":"30","errMsg":"데이터가 존재하지 않습니다."}
서울강서구  201_201A_516_51601 → {"err":"30","errMsg":"데이터가 존재하지 않습니다."}
```

**KOSIS 쪽 빈 노드다.** 목록에는 존재하지만 표가 0개다. 트리는 리프가 있는 경로만 기록하므로
빈 노드가 안 나타나는 게 정상이다. 실제로 서울은 표를 가진 단위가 3개뿐이다
(`서울특별시기본통계` 443표 / `구로구` 191표 / `강북구` 196표). **유실이 아니다.**

#### 검증 3 — 지자체 기본통계 61,471표의 형제 규칙성 (API 호출 0회)

`지역통계 > 지자체 기본통계`는 192개 단위가 같은 소분류 15종을 반복하는 규칙적 구조라,
형제와 비교하면 손실을 내부적으로 탐지할 수 있다.

| 누락 소분류 수 | 지자체 수 |
|---|---|
| 0개 (완전) | **169** |
| 1개 | 13 |
| 2개 | 2 |
| 3~7개 | 8 |

누락 사례를 보면 손실 패턴이 아니다.

- `노동` 1개만 빠진 11곳이 전부 **소규모 자치구·군**(부산 연제·사하·기장·북·사상·강서구,
  인천 동구·옹진군·강화군, 울산 남구, 전북 장수군) — 노동 통계를 작성하지 않는 것이 자연스럽다.
- 3개 이상 빠진 8곳은 대부분 **광역 본청**(서울·인천·제주·울산·부산·대구 기본통계)으로,
  본청은 시군구와 소분류 구성이 다르다.
- 표 수가 비정상적으로 적은 단위가 없다(완전한 169곳: 최소 132 / 중위 258 / 최대 5,264,
  불완전한 23곳: 110 ~ 1,041). **서브트리가 잘리면 표 수가 0에 가까워지는데 그런 사례가 없다.**

#### 종합 판정

| 항목 | 결과 |
|---|---|
| 검증한 표 | 2,703(재크롤) + 61,471(구조검사) = **64,174 / 265,094 = 24.2%** |
| 발견된 손실 | **0건** |
| 미검증 구간 | 지역통계 잔여 약 96,000표, 대형 대분류(B 사회일반 12,226 / K1 농림 11,275 / N2 과학·기술 9,606 / J2 기업경영 8,657 / N1 정보통신 8,571 …) |

**"손실이 없다"가 아니라 "검증한 24%에서는 손실이 없었고, 나머지는 여전히 증명되지 않았다"**
가 정확한 표현이다. 전량 확정이 필요하면 §6-16의 레시피로 약 2.5시간이면 끝난다.

## 2. ② `kosis_meta_enricher.py` — 차원·항목·시점·단위 보강

### 2.1 하는 일

표마다 `getMeta`를 호출한다.

| type | 얻는 것 | 쓰이는 곳 |
|---|---|---|
| `ITM` | 차원명(`OBJ_NM`) + 차원값(`ITM_NM`) + 항목 + 단위 | `doc_meta_text` / `doc_item_index` |
| `PRD` | 수록주기, 시작~최신 시점 | payload 필터 |
| `UNIT` | 단위(%, 명 …) — **ITM에서 단위를 못 얻었을 때만** | 단위 보강 |

`parse_itm_rows`(`:233`)의 핵심 아이디어: 모든 행이 `(OBJ_ID, ITM_ID/ITM_NM)` 쌍인데,
`OBJ_ID == "ITEM"`이면 진짜 '항목'이고 그 외 축(A=행정구역, YRE=연령)의 행은 그 차원의
'값'(전국, 서울특별시, 종로구 …)이다. 이 구분이 ③에서 **"차원명은 임베딩, 차원값은 BM25"**로
갈리는 근거가 된다.

### 2.2 잘 되어 있는 부분

4개 스크립트 중 가장 견고하다. 공유 `RateLimiter`가 잠금으로 다음 호출 슬롯을 원자적으로
예약해 워커 수와 무관하게 분당 호출을 캡하고(`:82-103`), 재시도·코드40 쿨다운·체크포인트·
`table_key` 기반 재개·연속실패 조기중단이 모두 있다. 조건부 UNIT 호출로 표당 호출을
3회 → 2~2.5회로 줄인 것도 실측 근거(표본 515건, 53%는 ITM만으로 단위 확보)가 붙어 있다.

**④를 재작성할 때 이 파일의 병렬화 패턴을 그대로 이식하면 된다.**

### 2.3 문제

#### (2-a) 전량 보강은 약 61시간 — 스키마를 되돌릴 수 없다

265,094표 × 2.5회 ÷ 180/분 ≈ **61시간**. 이미 완료돼 있어(v4, 265,082건) 지금은 문제가 아니지만,
필드를 추가하려고 재실행하면 비용이 다시 발생한다. **(1-d)가 단순 누락이 아니라 비싼 누락인 이유.**

#### (2-b) `latest_period`가 문자열 max다

```python
"latest_period": max(ends) if ends else None,
```
(`:312`)

`"2026.06"` vs `"2025"`는 앞자리부터 비교되어 맞지만, 월이 0-패딩 안 된 표에서는
`"2025.9" > "2025.10"`으로 뒤집힌다. 분기 표기(`2025.2/4`)도 섞인다. payload 프리필터로
"최근 3년" 조건을 걸 계획이면 오차가 생긴다.

#### (2-c) `load_done_keys`가 1.4 GB를 전량 스캔한다

재개할 때마다 JSONL 전체를 파싱한다(`:213`). 체크포인트 파일이 옆에 있는데도 쓰지 않는다.

## 3. ③ `kosis_catalog_builder.py` — 색인용 카탈로그 만들기

### 3.1 하는 일 — 설계상 가장 중요한 결정

v1은 표 하나를 `document_text` 한 필드로 만들었다.

```
"누적 혼인 비율 101 2025010 인구 인구동태패널통계 혼인·출산 비율"
```

dense 임베딩과 sparse(BM25)의 요구가 정반대다 — 임베딩은 짧고 의미가 밀집해야 하고, BM25는
매칭될 토큰이 없으면 못 찾으니 망라적이어야 한다. 게다가 `101`, `2025010`은 임베딩에 의미를
0으로 기여하면서 벡터를 끌어당긴다. 그래서 v2는 셋으로 쪼갠다.

```
doc_meta_text  = tbl_name | category_paths | 차원'명'      ← 임베딩 전용
doc_item_index = 항목명 + 차원'값' 전부                     ← BM25 전용
payload        = org_id, units, period_types, …             ← 필터 전용
```

```json
  "doc_item_index": "비율 전체 남자 여자 1983 1984 1985 …",
```

### 3.2 이 분리는 성공했다 — 손댈 필요 없음

합쳐 넣었을 때 1.7%가 한도를 초과했던 문제가 완전히 해소됐다. 토큰 여유가 압도적이라는 점은

### 3.3 문제

#### (3-a) `doc_item_index`를 아무도 읽지 않는다 — 카탈로그 43%가 죽은 용량

필드별 용량 실측(`kosis_catalog_v4.jsonl`, 265,094행):

| 필드 | 용량 | 비중 |
|---|---|---|
| **`doc_item_index`** | 109.4 MB | **43.4%** |
| `items` | 28.8 MB | 11.4% |
| `dimensions` | 27.8 MB | 11.0% |
| `doc_meta_text` | 21.7 MB | 8.6% |
| `source` (265k번 반복되는 동일 문자열) | 16.2 MB | 6.4% |
| `category_paths` | 15.4 MB | 6.1% |
| 나머지 12개 필드 합 | 32.4 MB | 11.1% |

그런데 레포 전체에서 `doc_item_index`를 소비하는 파이썬 코드가 **없다**(생산자 2개와 문서에만
등장). ④는 payload에도 넣지 않는다. 그리고 실제 BM25를 하는
`archive/260722/src/v2/search_hybrid_v2.py`를 보면:

```python
"""Okapi BM25 whose document is exactly Catalog v2 doc_meta_text."""
texts = [str(row.get("doc_meta_text") or "").strip() for row in rows]
```

**BM25에 `doc_meta_text`를 먹이고 있다.** ③이 "BM25 전용"으로 만든 필드를 BM25가 쓰지 않는다.
결과적으로 "종로구" 토큰을 인덱스에 넣으려고 26만 표에서 차원값을 긁어모은 노력이 검색에
반영되지 않는다. **설계 의도와 구현이 어긋난 지점이며, 둘 중 하나를 정해야 한다.**

- 살린다 → `search_hybrid_v2.py`의 BM25 문서를 `doc_meta_text + doc_item_index`로 바꾸고 (3-b) 상한 적용
- 버린다 → 카탈로그가 533 MB → 약 300 MB로 줄고 ④의 적재 비용도 준다

`source` 필드(6.4%)는 265k번 반복되는 상수 문자열이므로 manifest로 옮기면 된다.

#### (3-b) `doc_item_index`에 길이 상한이 없다

최대 **222,034자**(읍면동 × 1세 단위 표). p99는 4,151자이므로 이 한 건이 극단값이다.
BM25 문서 길이 정규화가 왜곡되고, sparse 벡터를 만들면 이 표가 posting list를 지배한다.

> 조치: 상한 4,000자(p99 수준) 적용.

#### (3-c) 메모리 — 스트리밍 가능한데 전량 적재

`load_meta`(`:83`)가 1.4 GB JSONL을 dict로 전량 적재하고, `flatten_leaves`가 100 MB 트리를
리스트로 펼친다. 둘이 동시에 RAM에 있어야 한다(수 GB).

#### (3-d) `--only-enriched`일 때 manifest 통계가 전체 기준이다

`:250`에서 `summary_all`을 계산한 뒤 `:252`에서 필터한다. 리포트 숫자와 파일 내용이 어긋난다.
실험 기록으로 쓰는 파일이라 혼란을 유발한다.

#### (3-e) `doc_meta_text`에 기관명·통계조사명이 없다

→ §5-①에서 다룬다.

## 4. ④ `kosis_v2_indexer.py` — Qdrant 색인 / **26만 색인 실패의 원인**

### 4.1 하는 일

표당 벡터 2개를 named vector로 넣는다.

```
doc_meta_vector ← doc_meta_text   (표명+경로+차원명, 문맥 풍부)
tbl_name_vector ← tbl_name        (표 이름만, 정확 매칭용)
```

`point_id`는 `uuid5(NAMESPACE, table_key)`(`:150`)로 결정론적이라 재실행 시 upsert가 멱등하다.
`EmbedCache`는 `sha256("모델버전|텍스트")`를 키로 JSONL에 append하고 seed 캐시에서 승격도 한다.
설계 골격 자체는 깔끔하다.

### 4.2 원인은 하나가 아니다 — 네 개의 벽이 순서대로 온다

#### 벽 1: 시간 — 약 78시간 (실측 근거 있음)

`index_summary.json`에 답이 이미 있다.

```json
{ "input_records": 515, "embedding_api_calls": 798, "elapsed_sec": 547.871 }
```

515행 = 547.9초, 즉 **행당 1.064초**. 26만 행으로 선형 확장하면 **약 78시간(3.3일)**.

임베딩 API 직접 측정 결과 순수 왕복은 **0.202초**인데, 실측 호출당은 547.9/798 = **0.686초**다.
차이의 원인:

- `embed_api`가 **매 호출마다** `load_api_key()` → `load_dotenv()`로 `.env`를 재파싱(`:47-52`)
- 캐시 append마다 파일 open/close(`:93-97`)

필요한 임베딩 수:

| 대상 | 건수 | 비고 |
|---|---|---|
| `doc_meta_text` | 265,094 | 거의 전부 유니크 |
| `tbl_name` | **129,118** | 26만 중 **51%가 이름 중복** ('행정구역' 등이 시군구마다 반복) |
| 합계 | **394,212회** | |

캐시가 절반을 막아주지만 **순차 실행**이라 시간은 그대로다. ②는 워커 8개 + 공유 RateLimiter를
갖췄는데, ④는 for 루프에서 한 건씩 부른다(`:214-222`). 같은 레포에서 검증된 패턴을 쓰지 않는다.

#### 벽 2: 메모리 — 캐시가 13 GB

`EmbedCache.__init__`이 캐시 파일 **전체를 파이썬 dict로** 적재한다(`:71`).

실측:

| 형태 | 벡터 1개당 | 394,212개 |
|---|---|---|
| JSONL 파일 | 12,428 B | **4.9 GB** |
| 파이썬 `dict[str, list[float]]` | 33,526 B | **13.2 GB** ← 대부분의 장비에서 `MemoryError` |

게다가 `load_records`도 533 MB 카탈로그를 전량 적재하는데(`:128`), ④가 실제로 쓰는 필드는
`table_key / org_id / org_name / tbl_id / tbl_name / doc_meta_text`뿐이다. 43%를 차지하는
`doc_item_index`를 읽어서 버린다.

#### 벽 3: 한 줄이 전체를 죽인다 (all-or-nothing)

```python
if not table_key or not doc_meta_text or not tbl_name:
    raise ValueError(f"line {line_number}: … 누락")
if table_key in seen:
    raise ValueError(f"line {line_number}: duplicate table_key={table_key}")
```
(`:139-143`)

`json.loads`도 감싸지 않았다. 26만 행 중 한 줄이 이상하면 **아무것도 색인되지 않고 끝난다.**
v4 카탈로그를 전량 검사한 결과 현재는 깨끗하다(`table_key` 중복 0, 빈 `doc_meta_text` 0,
빈 `tbl_name` 0). 그러나 78시간짜리 작업의 검증이 all-or-nothing이라는 구조는 그대로다.

**upsert 레벨 재개도 없다.** 20만 건에서 죽으면 재실행 시 결과는 맞지만(멱등) 캐시 히트
20만 건을 다시 읽고 20만 포인트를 다시 upsert한다.

#### 벽 4: Qdrant local 모드에는 인덱스가 없다

```python
client = QdrantClient(path=str(args.db_path))    # 임베디드 로컬 모드
```
(`:192`)

설치된 `qdrant-client 1.18.0`의 `local_collection.py` 주석: **"LocalCollection does not do
indexing"** — HNSW 없이 **전량 브루트포스** 스캔이다.

- 벡터 원본만 265,094 × 2 × 1024 × 4B = **2.17 GB** (전부 RAM)
- 검색 1회 = 26만 × 1024차원 내적을 named vector 2개에 대해
- 평가셋 300건이면 이게 600번

컬렉션 생성 시 `hnsw_config` / `quantization_config` / `on_disk` / `on_disk_payload`를 전혀
지정하지 않는다(`:206-212`). 26만 규모에서는 **Docker 서버 모드 + scalar quantization이 사실상
필수**다.

### 4.3 그 외

#### payload가 너무 얇다

```python
payload={"table_key", "org_id", "org_name", "tbl_id", "tbl_name", "doc_meta_text", "catalog_version"}
```
(`:223-231`)

③에서 만든 `category_paths`, `units`, `period_types`, `latest_period`, `stat_id`, `meta_status`가
**하나도 안 들어간다.** ③ docstring이 "payload — 필터 전용"이라 선언한 값들인데 ④가 받지 않는다.
`create_payload_index`도 호출하지 않아 넣더라도 필터가 풀스캔이다.

#### 기타

| 항목 | 현재 | 문제 |
|---|---|---|
| `batch_size=32` + `wait=True` | 8,285회 블로킹 flush | 256~1000 + 마지막에만 wait |
| 재시도 `range(3)`, sleep 1·2초 (`:114-123`) | 지터 없음, `Retry-After` 무시 | 429 대량 발생 시 동조 재시도 |
| `"run_date": "2026-07-22"` 하드코딩 | 출처 기록이 틀림 | 실행 시각으로 |
| `--limit` | `table_key` 정렬 앞부분 = org 101 편향 | 표본은 대분류 층화 추출 |
| `PROJECT_ROOT = parents[4]` (`:22`) | 파일 위치에 강결합 | 파일 이동 시 조용히 깨짐 |
| sparse 벡터 없음 | 하이브리드가 색인에 반영 안 됨 | 기존 `kosis_tables` 컬렉션에는 `lexical` sparse가 있음 |

### 5.0 파일 자체는 정상이다

### 5.1 현황: 64.5% → 40.6% (절반만 고쳐졌다)

| | org_id 종류 | 사전 커버 | 이름 없는 표 |

`kosis_catalog_v4.jsonl`은 아직 옛 사전으로 만든 것이라 64.5%다. 재빌드하면 40.6%가 된다.

### 5.2 왜 40%가 남는가 — `MT_OTITLE` 뷰의 구조적 한계

새 사전 181개의 출처를 확인했다. `statisticsList.do?vwCd=MT_OTITLE&parentListId=`(빈 값)이
**정확히 181개**를 반환한다.


즉 KOSIS '기관별' 뷰 루트를 그대로 받아온 것이다. 문제는 **이 뷰에 기초자치단체가 없다는 것**이다.

| 6xx | 46,268 | 시·군·구 (611=수원시, 619=안산시, 620=고양시, 651=춘천시 …) |
| 7xx | 43,366 | 시·군·구 (711=전주시, 714=정읍시 …) |
| 5xx | 9,380 | 시·군·구 |
| 8xx | 4,487 | 시·군·구 |
| 2xx | 3,484 | **205 광주광역시, 215 전라남도** |
| 1xx | 508 | 중앙부처 잔여 |
| 4xx | 6 | |
| **합** | **107,499** | |

`MT_OTITLE`에 6xx/7xx/5xx/8xx가 한 건도 없다(확인함). **이 방법으로는 구조적으로 채울 수 없다.**

### 5.3 2xx 누락은 행정구역 통합 때문이다

사전의 2xx는 `201~204, 206~214, 216~218`로 **205와 215가 빠져 있다.** 원인은 사전 안에 있었다.

```json
"209": "전남광주통합특별시"
```

광주(205)와 전남(215)이 통합돼 `MT_OTITLE`에는 통합 법인(209)만 남았고, 205/215로 등록된 기존
표 3,484건이 이름을 잃었다. **현행 기관 목록과 과거 표의 org_id가 어긋나는 구조적 문제**이므로,
앞으로 통합·개편이 있을 때마다 반복된다.

### 5.4 더 근본적인 문제: `org_id → 기관명`은 1:1이 아니다

`statisticsSearch.do`는 응답에 `ORG_NM`을 준다. 7개 키워드로 700건을 뽑아 `org_id`별 `ORG_NM`
분포를 세어보면:

```
101 → 국가데이터처 152건, 행정안전부 4, 부산광역시 3, 울산광역시 3, 충청남도 3, … (총 17종)
354 → 국민건강보험공단 58건, 건강보험심사평가원 2건
```

`org_id 101`은 통계 **호스팅** 기관(국가데이터처)이고, `ORG_NM`은 표별 **작성** 기관이다.
예: `DT_1B04005N`(주민등록인구)은 `org_id=101`이지만 작성기관은 행정안전부다.

**따라서 `org_id` 하나에 기관명 하나를 매핑하는 사전 자체가 원리적으로 부정확하다.** 현재 사전은
`354`를 '건강보험심사평가원'으로 적지만 그 org_id 표의 대다수는 국민건강보험공단 자료다.

#### (b) `category_paths`에서 파싱 — API 호출 0회

6xx/7xx는 경로에 답이 들어 있다.

```
611  지역통계 > 지자체 기본통계 > 경기도 > 경기도수원시기본통계 > 토지 및 기후
619  지역통계 > 지자체 기본통계 > 경기도 > 경기도안산시기본통계 > 토지 및 기후
711  지역통계 > 경제 및 산업 > 전북특별자치도 > 전주시전통시장및상점가조사
791  지역통계 > 지자체 기본통계 > 경상남도 > 경상남도창원시기본통계 > 토지 및 기후
```

`"…기본통계"` 접미사를 떼고 광역 접두를 분리하면 `경기도 수원시`를 얻는다. **크롤링 없이
오늘 안에 40% → 거의 0%로 만들 수 있는 경로다.**

### 선택 — 트리 완전성 전량 확정 (약 2.5시간, API 26,808회)

§1.3의 검증 1을 30개 대분류 전체로 확대하면 완전성을 확정할 수 있다. 표 집합을 전부 대조할
필요도 없다 — **노드 수를 세어 `calls`와 비교하는 것만으로 예외 실패를 탐지**할 수 있고,
불일치가 나온 대분류만 표 단위로 대조하면 된다.

| 항목 | 값 |
|---|---|
| 필요 호출 | 26,808회 (= 트리에 기록된 `calls` 총합) |
| 소요 | 26,808 × 0.34s ≈ **2시간 32분** |
| 주의 | KOSIS 분당 한도는 **API 키 단위 합산**이므로, ②(enricher) 등 다른 크롤을 같은 키로 동시에 돌리면 안 된다 |
| 산출물 | 대분류별 `(기존 표, 재크롤 표, calls, 재크롤 노드, 누락 표 목록)` |

미검증 구간이 76%이고 그중 지역통계가 약 96,000표(36%)를 차지하므로, 색인 파이프라인을
확정하기 전에 한 번은 돌려두는 것이 안전하다.
