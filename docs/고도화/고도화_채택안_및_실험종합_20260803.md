# 고도화 채택안과 실험 종합 — baseline 대비 무엇을 바꾸고 무엇을 지킬 것인가

작성일: 2026-08-03
범위: 기사 입력 → KOSIS 검색 질의 생성까지. 임베딩·리랭킹·답변 생성은 담당이 다르므로
채택 판정만 하고 구현은 다루지 않는다.

> **검색 gold v2 정정:** 본문의 검색 Recall@10 `0.394`는 표명 기반 dev 진단값으로
> 유지하되 공식 성능값으로 사용하지 않는다. 동일 표명 key 자동 동등화가 전국·지역
> 표를 섞는 문제가 확인되어 exact `org_id:tbl_id` 사람 확정 계약으로 재개방했다.
> 현재 exact-key 확정 10건은 후보 선택 편향이 있으므로 성능 주장이 아니며, v2
> 11그룹 재검토와 독립 test gold 전까지 G0-H는 `[~]`이다.

## 1. 비교 대상 — baseline 파이프라인

```text
① 정규표현식으로 주장 문장 추출
② HCX-007로 구조화 (주장별 지표·대상·시점·수치·단위·비교조건)
③ 통계표 카탈로그로 매핑
④ 임베딩 3종 → RRF
⑤ NCP reranker
⑥ NCP rag-reasoning으로 답변 생성
```

baseline 실측(2026-07-22 기준, 500문장 표본):

| 지표 | 값 |
|---|---:|
| claim detection P / R / F1 | 1.000 / 0.781 / **0.877** |
| claim class macro F1 | 0.329 |
| source scope exact | 0.780 |
| 검색 참고 후보 MRR (hybrid v3, 500) | 0.267 |

**검색 쪽 0.267은 Recall이 아니다.** 당시 gold table mapping이 없었고, 보고서 자신이
"샘플링 참고 후보 일치율"이라고 명시했다.

## 2. 결론 — 단계별 채택 판정

| 단계 | 판정 | 무엇을 |
|---|---|---|
| ① 정규식 값 추출 | **유지(동결)** | 역할만 재정의. 주장 선별기가 아니라 값 후보 생성기 |
| ② HCX 구조화 | **교체** | 모델 역할을 6필드 생성 → **기사 레이아웃 라벨링**으로 축소 |
| ②′ 필드 생성 | **신규(결정론)** | 레이아웃 × 값에서 **합성**. 모델이 만들지 않음 |
| ②″ 검증대상 판정 | **교체** | 어휘 규칙 627개 → **출처 region 1개 기준** |
| ③ 카탈로그 매핑 | **계약 교체** | 단일 문자열 → **역할 붙은 질의 1~3개**, 연결 금지 |
| ④ 임베딩 3종 RRF | **유지** | 바꿀 근거 없음. 단 4.5절 주의사항 있음 |
| ⑤ NCP reranker | **유지** | 우리 측정 범위 밖 |
| ⑥ rag-reasoning | **유지** | 우리 측정 범위 밖 |

**바꾸자고 제안하는 것은 ②와 ③뿐이다.** ①은 유지, ④~⑥은 건드리지 않는다.

## 3. 채택 항목과 근거

### 3.1 HCX의 역할을 축소한다 — 가장 큰 변경

baseline과 그 후속(r11~r16i)은 **주장마다 여섯 필드를 모델이 직접 만들게** 했다.

```
개별 필드 정확도   0.12 ~ 0.61
여섯 필드 동시     0.009        ← 곱해진다
```

필드를 독립적으로 유도하면 오차도 독립이라 결합에서 무너진다. r17은 반대로 한다.

```
모델이 하는 일   기사 문장별로 "어떤 지표가 이 문장을 지배하는가",
                "이 수치의 출처는 어디인가" 를 라벨링 (L2)
코드가 하는 일   그 레이아웃에서 값마다 역할을 읽고(L3),
                필드를 정규화하고(L4), 보낼지 결정한다(L5)
```

**최종 필드는 모델이 생성하지 않고 (레이아웃 라벨 × 값 span)으로 합성된다.** 오차가
한 층에 귀속되므로 어디를 고칠지 알 수 있다.

### 3.2 차단을 veto에서 점수로 바꾼다

baseline 계열은 조건 불충족 시 주장을 **버렸다**. 그 결과:

| | r16i | r17 holdout-1 |
|---|---:|---:|
| 차단 정밀도 (버린 것 중 옳게 버린 비율) | **0.330** | **1.000** |
| routing recall | 0.411 | 1.000 |

r16i는 검증 가능한 주장을 **세 개 버릴 때 하나만 옳게** 버렸다. 134건 중 90건을
차단했고 그 중 63건이 실제 KOSIS 대상이었다.

근거는 비대칭성이다. **잘못 보낸 주장은 뒤에서 `UNVERIFIABLE`로 끝나지만(허용된
결과), 버려진 주장은 복구가 불가능하다.**

### 3.3 어휘 규칙 627개를 출처 region 1개로 대체한다

r16i의 차단은 161개 상태코드와 627개 한국어 표면형으로 이뤄져 있었다. 그 중 한
규칙(지표 어절이 값과 같은 문장에 문자적으로 등장할 것)이 **차단의 1/3**을 만들었고,
그 30건 중 25건이 정답 손실이었다. 한국어 기사는 지표를 리드에서 한 번만 말하므로
이 규칙은 **긴 기사를 구조적으로 탈락**시킨다.

r17의 판정 전부:

```python
if subtype in {"민간조사","정책목표","잠정추산","법정기준"}: OUT_OF_SCOPE
if subtype == "공식집계":                                   KOSIS_CANDIDATE (1.0)
if indicator:                                              KOSIS_CANDIDATE (0.5)
else:                                                      NOT_CLAIM
```

**분리 실험으로 확인된 것**: 리터럴을 끄면 recall은 0.411로 불변이고 false positive만
10건 는다. 즉 **리터럴은 recall이 아니라 precision 작업을 하고 있었고, recall 병목은
위 anchor 구조 규칙 하나였다.**

### 3.4 검색 질의를 역할 붙은 1~3개로 내보낸다

정답 KOSIS 표가 확정된 33건 측정(어휘 검색 기준):

| 질의 구성 | Recall@10 |
|---|---:|
| indicator + item·population **연결** | 0.303 |
| indicator **단독** | 0.333 |
| 변형을 **따로 실행** (각 K=10) | **0.394** |
| 변형 실행 후 **하나의 10개로 융합** (점수·RRF 모두) | 0.333 |
| *상한*: 정답 표명 자체로 검색 | 0.970 |

- **연결하면 손해다.** `item`·`population`은 표의 **분류축**이므로 질의에 섞으면
  매칭이 축 이름 쪽으로 끌린다.
- **따로 실행하면 이득이 있다.** 지표가 떨군 어휘를 원문 문장이 갖는 경우가 있다.
- **그 이득의 출처는 후보 예산이다.** 하나의 Top-10으로 합치면 사라진다.

### 3.5 평가 표본을 층화해 동결한다 — 코드가 아닌 방법론

r16i의 `dev 1.000 → holdout 0.355` 붕괴는 절반이 과적합이 아니라 **모집단 불일치**
였다. holdout 8기사는 전부 KOSIS 등재 출처였고 dev 기사는 아니었다.

r17은 같은 stratum에서 값 밀도로 층화해 dev 12 / holdout-1 12 / sealed holdout-2 12로
나눴다. 결과:

```
dev-12       F1 0.804
holdout-1    F1 0.880   ← 독립 표본이 개발셋보다 높다
```

붕괴가 재현되지 않았다. **다만 "holdout이 더 쉽다"로도 읽히므로 우월성의 근거로는
쓰지 않는다.**

## 4. baseline 대비 실제 수치

| 지표 | baseline | r16i | **r17** | 표본 |
|---|---:|---:|---:|---|
| claim/routing F1 | 0.877 | 0.583 | **0.880** | 아래 주의 |
| recall | 0.781 | 0.411 | **1.000** | |
| 차단 정밀도 | 미측정 | 0.330 | **1.000** | |
| 여섯 필드 동시 exact | — | 0.009 | 0.020 | dev-6 |
| 3필드 결합 exact | — | 0.108 | 0.118 | dev-6 |
| 검색 Recall@10 | 없음(MRR 0.267) | 없음 | **0.394** | gold 33 |

**F1만 보면 baseline 0.877과 r17 0.880이 비슷해 보이지만 같은 것을 재지 않았다.**

| | baseline | r17 |
|---|---|---|
| 단위 | claim | value |
| 표본 | 500문장 | holdout 12기사 246값 |
| 질문 | "이것이 주장인가" | "KOSIS로 검증 가능한가" |

**비교 가능한 것은 recall이다.** baseline은 실제 claim 473건 중 **103건(22%)을
비주장으로 놓쳤다.** r17은 L1이 찾은 값 중 정답을 하나도 놓치지 않았다(end-to-end
상한은 L1 recall 0.968).

## 5. 실험 경과

### 5.1 r11~r16i — 36시간, 10회 교정, 실패

같은 5~6기사에서 프롬프트와 규칙을 반복 교정했다. 세 원인이 확인됐다.

1. **병목이 선택이 아니라 차단이었다.** semantic selection recall을 0.661 → 0.960으로
   올렸는데 최종 routing recall은 0.430 → 0.411로 **움직이지 않았다.**
2. **교정 수단이 리터럴 추가뿐이어서** 고유 표면형 627개, 상태코드 161종이 쌓였다.
3. **dev와 holdout이 다른 모집단이었다.**

이 지점에서 프롬프트·규칙 교정을 중단하고 층 분리로 전환했다.

### 5.2 r17 — 층 분리

```
L1  값 후보 추출          [동결]    recall 0.968
L2  기사 단위 segmentation [모델]    HCX-007
L3  역할 배정             [결정론]   상속 · 국소 override · fragment 합성
L4  필드 정규화           [결정론]   기간·수식어 분리, 측정유형
L5  라우팅                [결정론]   출처 region 기준, threshold 0.5
```

라벨링은 세 번 했다. L2 문장 라벨 98건, 라우팅 gold 246건(holdout-1), 검색 gold 55건.

### 5.3 측정에서 걸러낸 오경보 세 건

기록해 두는 이유는 **같은 함정이 반복되기 때문**이다.

| 오경보 | 실제 원인 |
|---|---|
| "근접 짝짓기가 0.618 → 0.355로 나쁘다" | 기사 기준 offset과 문장 기준 offset을 비교했다. 고치니 0.605로 차이 없음 |
| "L3가 0.618 → 0.568로 회귀했다" | L2 예측 파일이 달랐다(`r4` vs `r5split`). 같은 입력에서는 0.605로 동일 |
| "리터럴을 지우면 recall이 떨어진다" | 실측하니 recall 불변, FP만 +10. precision 작업이었다 |

**셋 다 입력을 고정하지 않아서 생겼다.** L2 예측 파일 5종의 L3 정확도는 0.307~0.605로
흩어진다 — 입력을 고정하지 않으면 층 지표는 아무 결론도 내지 못한다.

## 6. 얻은 인사이트

### 6.1 LLM에게 최종 산출물을 만들게 하지 않는다

여섯 필드를 모델이 만들면 0.009, 레이아웃만 만들게 하고 코드가 합성하면 routing이
0.880이 된다. **모델은 "무엇이 무엇을 지배하는가" 같은 판단에 쓰고, 그 판단을
조합해 산출물을 만드는 일은 코드가 한다.**

### 6.2 차단 정밀도를 보지 않으면 실패가 보이지 않는다

r16i는 precision 1.000이었다. 좋아 보인다. 그런데 차단 정밀도가 0.330이었다 —
**버린 것의 2/3이 정답이었다.** precision/recall만 보고 있었으면 이 계약을 계속
밀었을 것이다. **비대칭 비용 구조에서는 "무엇을 버렸는가"를 별도 지표로 봐야 한다.**

### 6.3 어휘 규칙은 recall이 아니라 precision 작업을 한다

627개 리터럴을 끄는 실험이 이것을 분리 증명했다. **규칙이 쌓이면 "이게 성능을 지탱한다"는
믿음이 생기지만, 끄고 재보기 전에는 무엇을 지탱하는지 알 수 없다.**

동시에: 그 리터럴들의 차단 이득은 **자기를 유발한 6기사에서만** 측정됐으므로
precision 1.000 자체가 부분적으로 dev 과적합 산물이었다.

### 6.4 성능 붕괴의 원인이 항상 과적합인 것은 아니다

표본 설계 실패는 코드로 해결되지 않는다. **모델을 고치기 전에 dev와 holdout이 같은
모집단인지 확인해야 한다.**

### 6.5 검색 실패의 원인은 순위가 아니라 어휘였다

```
Recall@3 = Recall@10 = 0.182     ← 4~10위에서 정답이 나온 적이 0회
K=100으로 늘려도 0.485
정답 표명으로 검색하면 0.970
```

**정답이 후보군에 진입 자체를 못 한다.** 기사 표현과 표 제목이 문자를 거의 공유하지
않기 때문이다.

```
1인당 국민소득   →  주요지표(연간지표)        공유 어휘 없음
근로소득세 수입  →  연도별 국세 징수실적       공유 어휘 없음
```

**dense retrieval의 필요성이 설계상 가정에서 측정된 사실로 바뀌었다.** 동시에 이 격차를
어휘 규칙으로 메우려는 시도는 하지 않기로 했다 — 표명 과적합이 되고, 3절 아키텍처상
dense의 몫이다.

### 6.6 구조화가 완벽해도 20%는 검증되지 않는다

검색 gold 55건 중 11건이 **KOSIS에 표 자체가 없다**(노년 부양비는 통계표가 아닌
PDF로만 존재). 추가로 9건은 표는 맞는데 분류축이 달라 셀 정렬 문제로 이관됐다.

**`UNVERIFIABLE`을 정상 출력으로 설계한 것이 실측으로 정당화됐다.** 없는 데이터를
있는 척하지 않는다.

## 7. 채택하지 않기로 한 것 / 반증된 것

| 방향 | 왜 |
|---|---|
| LLM이 최종 여섯 필드 생성 | 0.009 |
| 어휘 규칙으로 결정론화 확대 | 627개까지 갔고 recall에 기여 0 |
| 문장당 단일 indicator 라벨 | gold에서 28문장이 복수 지표 |
| K 확대로 검색 개선 | Recall@3 == Recall@10 |
| indicator를 표명 어휘로 재작성 | dense의 몫. 하면 표명 과적합 |
| L1 후보 추출기 개선 | recall 0.968, 남은 FN은 상위 층에서 회수 |
| 자동 파생 라벨을 gold로 사용 | 평가가 자기 자신을 채점하게 됨 |

## 8. 남은 한계 — 정직하게

1. **검색 조건의 표현 정확도가 낮다.** 3필드 동시 exact **0.118**. 값을 버리지는
   않지만 붙여주는 조건은 8건 중 7건이 어딘가 어긋난다. `indicator` exact 0.216 /
   relaxed 0.686이므로 완전 오답이 아니라 표현 어긋남이다.
2. **이것이 검색 성능에 얼마나 영향을 주는지 아직 모른다.** `gold indicator 검색` vs
   `예측 indicator 검색`의 Recall@K 차이(ablation)로만 판정할 수 있고, 그건 팀의
   검색기가 나와야 돌린다. **"임베딩이 메워줄 것"은 현재 가설이다.**
3. **라우팅 precision 0.785.** 오라우팅 50건 중 44건이 비통계 기사 4건에 몰려 있다.
   통계 기사에서는 1.000이다.
4. **Gate B 3요건 중 1개만 독립 표본에서 통과했다.** 나머지 둘(필드 결합, 층별 지표)은
   10회 넘게 교정된 dev-6에서만 측정됐다.
5. **유효 표본이 작다.** 라우팅 12기사, 검색 gold 10기사. 한 기사 안의 값들은 오차가
